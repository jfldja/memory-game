# 驗收測試 Skill

本 skill 規範「如何把已簽核的需求與設計變成能證明合格、也能證明不合格的驗收測試」。它與專案無關；文中出現的編號、檔名、數值、指令都標示為「範例」。

搭配使用：開發流程與角色依 `agent-dev-workflow`（特別是第 3.1 節測試分工、第 4.3 節驗收測試骨架、第 5 節發現問題時）；測試層與骨架計畫依專案的設計文件。

---

## 0. 核心原則

1. **需求是判定依據，設計是操作依據。** 驗收測試判定的是需求文件的 Then；選擇器、資料格式、測試輔助依設計。兩者衝突時以需求為準並回報設計。
2. **每個實際測試都要證明自己會失敗。** 只看過綠燈的測試，可能什麼都沒驗證。轉實測時以變異（第 4 節）確認它在產品錯誤時會變紅。
3. **期望值獨立於受測程式。** 期望值從需求或設計文件抄寫，不由受測程式或受測腳本產生。
4. **不修改產品程式碼與檢查腳本。** 發現它們有問題，記錄並回報（agent-dev-workflow 5.1、5.2），不在測試中繞過，也不放寬判定。
5. **略過不是通過。** 略過的骨架只讓編號檢查通過，不算驗收；交付與報告中分開列出。

---

## 1. 輸入與產出

**輸入（缺任何一項就停下來回報）：**

| 輸入 | 用途 |
|---|---|
| 已簽核的需求文件 | 驗收標準（Given／When／Then）、非功能需求的量測方法、測試命名規則 |
| 已簽核的設計文件 | 驗收骨架計畫（編號、測試層、檔案、轉實測的變更）、畫面測試介面（選擇器與屬性）、測試輔助的設計、CI 設定 |
| 實作 agent 的交接 | 檢查腳本的介面與判定規則、建置與伺服器指令、哪些畫面已存在 |
| 專案工作規範（若有） | 報告位置、skill 版本號的證明方式 |

**產出：**

| 產出 | 交給 |
|---|---|
| 驗收測試（骨架與實際測試） | 審查 agent（經變更請求） |
| 本機執行結果：各測試層、各環境的通過／失敗／略過數，未能在本機執行的環境 | 變更請求說明、統籌 agent |
| 缺陷紀錄與上游問題紀錄 | 統籌 agent（轉給負責的階段） |
| 測試報告（系統測試階段） | 產品負責人 |
| 本 skill 的修改 | 依第 9 節 |

## 2. 步驟

1. **上工檢查**（agent-dev-workflow 第 1 節）。讀需求的驗收標準全文（不只標題）、設計的骨架計畫、畫面測試介面與 CI 設定。
2. **核對骨架清單。** 以腳本或檢查腳本本身解析需求，確認必要編號數量與設計的骨架計畫相同；不同時回報設計，不自行增減。
3. **建立骨架**（第 3 節）。
4. **轉實測**（第 4 節）：只轉本變更負責的項目；確認 Given／When 所需畫面與操作已存在，不存在時依 agent-dev-workflow 5.1 回報，不得自行加入捷徑入口。
5. **變異檢查**（第 4.3 節）。
6. **本機執行**（第 6 節）：全部測試層、編號檢查；記錄本機沒有的環境交由 CI。
7. **提交**（第 7 節）：每個 commit 都讓編號檢查維持通過。
8. **自我審查**（第 8 節），交付。

---

## 3. 驗收測試骨架

- 名稱以編號開頭，後接 Then 的摘要（範例：`'AC-X-5 翻錯 1 秒後翻回：0.9 秒仍正面、1.1 秒已背面'`）。摘要寫需求的判定點，讓骨架本身就是待辦清單。
- 檔案開頭註解寫明：對應的計畫章節、預定轉實測的變更、轉實測時必須遵守的設計注意事項。
- 用測試框架原生的略過寫法宣告（範例：`test.skip(名稱, 空函式)`），且這種寫法必須是編號檢查認得的「略過」。
- **多範圍編號分開命名**（範例：`'NFR-5 選單：…'`、`'NFR-5 結果畫面：…'`），未完成的範圍保持略過。量測方法要求多個長度或條件時，也各一個測試。
- 同一編號跨兩個測試層時，兩層各一個骨架，名稱標明範圍（範例：「統計」「連續遊玩」）。
- 啟用編號檢查的變更必須同時包含全部骨架（agent-dev-workflow 4.3）。

---

## 4. 轉實測

### 4.1 編號覆蓋檢查本身的驗收（範例：「每個編號都有測試，缺一個 CI 就失敗」）

這類驗收測的是檢查腳本，而檢查腳本採計的正是「測試名稱」，因此特別容易自我掩蓋：

- **本檔的測試名稱不得含其他必要編號。** 例如反例「刪除 AC-X-5 的測試後應失敗」，如果這個反例測試自己的名稱含 `AC-X-5`，刪除真正的測試後編號仍被這個名稱涵蓋，反例永遠失敗不了。說明文字改用描述（「需求指定之編號」），並加一個測試檢查本檔名稱只含自身編號。
- **期望的編號清單從設計的骨架計畫抄寫**，與腳本解析結果比對；不得用腳本的輸出當期望值。
- **反例在暫存複本上做，並有對照組。** 複製需求文件、設定檔、檢查腳本與整個測試目錄；先確認複本「刪除前通過」，再刪除目標測試，確認「刪除後失敗，且只回報該編號」。沒有對照組時，複本本來就失敗也會讓反例通過。
- **刪除要像真的刪除一個測試。** 刪除整個呼叫，之後以語法檢查（範例：`node --check`）確認檔案仍合法；刪除的程式不要與受測腳本共用同一個解析器，以免兩邊的同一個錯誤互相掩蓋。
- **除了呼叫函式，也執行 CI 實際執行的指令**，確認結束代碼。函式通過但 CLI 沒有以非零結束時，CI 仍不會失敗。
- 涵蓋完整編號比對（範例：`AC-X-10` 不涵蓋 `AC-X-1`）、註解中的編號不算、每一種略過寫法都被判定為略過。
- **每個反例只能因目標規則而失敗。** 檢查腳本有多條規則時（範例：「不允許的略過寫法」「非骨架測試要有斷言」「名稱不得重複」），反例的其他部分必須符合所有其他規則（範例：本體仍放一個斷言呼叫），並斷言「在標示的那一行、以目標規則」失敗，不能只斷言「整體失敗」。否則目標規則失效時，反例仍會因為別的規則失敗而通過。做法：測試資料中以標記（範例：行尾 `// ←`）標示應被指出的行，在同一位置放一個結構相同、合乎規則的對照組，先確認對照組通過。
- **反例要涵蓋規則的每一條邊界，不只禁止的寫法。** 範例：唯一允許的骨架寫法，要同時有「允許的形式都通過」（可帶參數、`async`、只有註解的本體）與「形狀稍有不同就失敗」（本體不為空、在區塊內、名稱為樣板字面值、函式運算式、多一個參數）；位置規則要涵蓋每一種不會被執行的位置與副檔名；「單元測試不得冒充驗收」要分別驗證「驗收測試還在時也失敗」與「只剩單元測試時不採計覆蓋」，並有非必要編號不受限的對照組。
- **以執行結果判定的檢查，用 CI 的指令實際跑一次反例。** 只呼叫判定函式，證明不了 reporter、結果檔、計數模組與檢查 CLI 串起來會失敗。在暫存目錄建立只含一個反例檔的最小版本庫（不要複製整個驗收目錄，否則會遞迴執行本檔），依序執行 CI 的測試指令與結果檢查指令，確認結束代碼與指出的判定項目。至少涵蓋：對照組通過、骨架只在「不允許略過」模式失敗、第一個斷言之前提前返回、斷言寫在不會執行的分支、吞掉失敗的斷言、靜態偵測看不到的執行期略過（範例：以動態組字的屬性名呼叫略過）；最後一項另外斷言靜態檢查確實沒有指出它，證明是執行結果抓到的。
- **在測試執行器之內啟動另一個測試執行器時，清除執行器的內部環境變數。** 範例：`node --test` 會以 `NODE_TEST_CONTEXT` 讓子行程改向父行程回報、不使用指定的 reporter，結果檔因此不會產生。
- **規則以檔案為單位時（範例：每個驗收測試檔都要自斷言模組匯入），只含骨架的檔案也要照做**，被匯入的模組與骨架檔案的修改放在同一個變更，否則檢查或載入會失敗。

### 4.2 端對端測試

- **不做會干擾其他測試的事。** 需要特殊建置（範例：指定 commit 的版本號）時，在暫存目錄以正式的建置指令建置、另起伺服器，不重建其他測試共用的輸出目錄（平行執行時會讓其他測試讀到半成品）。
- **不依賴 CI 是否傳入某個環境變數。** 測試自己能取得的資訊（範例：`git rev-parse HEAD`）自己取得；從環境變數取得的值只作額外檢查，並在沒有時明確說明檢查了什麼。
- **注意 CI 的簽出內容。** 變更請求的 CI 常簽出合併 commit 且為淺層複製（範例：GitHub `pull_request` 事件），變更請求自身的 commit 可能不在本機；需要以 git 反查 commit 時，用實際簽出的 commit。
- **證明「沒有發生」的測試要先證明「有在運作」。** 範例：檢查「沒有對外部網域的請求」前，先確認頁面腳本已執行、至少記錄到頁面本身的請求，否則頁面沒載入也會通過。
- **在最外層記錄。** 網路請求在瀏覽器 context 層、`goto` 之前開始記錄（含 worker 與失敗的請求）；只排除不經網路的 URL 配置（`data:`、`blob:`、`about:`），其餘一律比對來源。
- 時鐘控制、停用元素的點擊、隱藏資訊的取得方式，依設計文件的測試注意事項；設計沒有寫時依 agent-dev-workflow 5.1 回報，不自行選一種。

### 4.2.1 斷言計數輔助（框架沒有內建斷言計數時）

設計要求「每個測試至少執行一次斷言、沒有被吞掉的失敗」，而框架沒有內建計數時（範例：`node:test`），測試端提供一個包裝斷言庫的模組，在每個測試結束時回報次數。撰寫時注意：

- **巢狀斷言只計外層一次。** 範例：`assert.throws(() => assert.equal(1, 2))` 的內層失敗是外層預期的結果；若內層也計數，會被判定為「吞掉失敗的斷言」。以呼叫深度判斷，只計最外層。非同步斷言（範例：`rejects`）的回呼在 `await` 之後才執行的部分不在同步深度內，寫明這個限制。
- **只包裝斷言函式。** 類別與非函式屬性（範例：`AssertionError`）原樣傳回；別名屬性（範例：`assert.strict`）傳回同一個包裝，否則經別名呼叫的斷言不被計數。
- **回傳 Promise 的斷言，以 Promise 被拒絕計為失敗。**
- **計數是行程內的全域狀態**，以「同一時間只執行一個測試」為前提。寫明不得在驗收測試中使用並行選項或子測試，否則計數混在一起。
- 回報方式依設計（範例：每個測試結束的 hook 以診斷訊息輸出），先實測略過的測試不執行 hook、回報能對應到正確的測試。
- 包裝模組本身也做變異檢查：拿掉失敗計數、改掉回報格式，確認以 CI 的指令執行的反例（4.1）會失敗。

### 4.3 變異檢查（每個轉實測的測試都做）

1. 以最小的錯誤讓產品不符需求：優先改**建置輸出或暫存複本**（範例：在輸出的頁面加入外部圖片、把版本號改成開發用預設值），不改原始碼，也不提交。
2. 執行該測試，確認失敗，且失敗訊息指出了錯誤。
3. 還原（重新建置），確認通過。
4. 把變異方式寫進 commit 訊息或變更請求說明，供審查者重做。
5. **受測對象是檢查腳本時**（範例：編號覆蓋檢查、執行結果檢查），變異對象是腳本中的每一條規則：逐條讓它失效（範例：從禁止清單移除一個名稱、讓「有斷言呼叫」恆為真、讓失敗時仍以 0 結束），確認至少一個反例失敗，且失敗的是針對該規則的那一個。沒有任何測試失敗的規則，就是驗收沒有涵蓋的規則。
6. **變異前先備份，不依賴版本控制還原。** 本變更新增、尚未追蹤的檔案（範例：新的測試輔助模組）無法以 `git checkout` 還原；以複製備份還原，最後以 `git status` 與重跑測試確認沒有留下變異。

## 5. 發現問題時

| 情況 | 處理 |
|---|---|
| 產品不符需求 | 缺陷紀錄：編號、重現步驟、預期、實際、受測 commit、優先級。不修改產品程式碼 |
| 檢查腳本或 CI 設定的漏洞（範例：某種略過寫法沒有被偵測） | 以最小的範例實際驗證，記錄輸入與輸出；回報實作 agent，若腳本照設計實作則回報設計 |
| 設計文件與需求不一致、測試介面不足 | 依 agent-dev-workflow 5.1 回報設計 agent |
| 需求本身不清楚 | 依 agent-dev-workflow 5.1 回報統籌 agent |
| 已簽核的設計變更讓既有驗收測試的期望不再成立（範例：設計收緊為「只允許一種略過寫法」，原本「各種略過寫法都可通過」的案例變成錯的） | 這是設計變更造成的驗收測試修改，不是為了讓測試通過而改測試：依新設計改寫期望（通常是原本的正例變成反例），在 commit 訊息與變更請求寫明依據的設計版本、章節與驗收編號；改寫後的案例照 4.3 做變異檢查。設計沒有明說、只能從實作推得的邊界（範例：骨架名稱可否為樣板字面值），在交付摘要列為假設交審查確認 |

**常被漏掉、值得主動驗證的檢查腳本漏洞（範例，視框架而定）：**

- 在測試本體內呼叫的執行期略過（範例：Playwright 的 `test.skip()`／`test.fixme(條件)`、`node:test` 的 `t.skip()`）：靜態掃描名稱的檢查看不到，「不允許略過」可被繞過。
- 框架的區塊變體（範例：`test.describe.serial`、`test.describe.parallel` 及其 `.skip`）：名稱不被採計，或其中的測試不被判定為略過。
- 掃描範圍包含模組單元測試：實作者的單元測試名稱若含驗收編號，會被當成驗收覆蓋，違反「寫程式的人不判定自己合格」。

---

## 6. 本機執行

- 依 CI 的順序執行：建置 → 單元層（含驗收的無瀏覽器層）→ 編號檢查 → 端對端層 → 需真實時間的量測（單一 worker）。
- 記錄每層的通過／失敗／略過數。略過數應等於仍未轉實測的骨架數，多出來的要查。
- 本機沒有的環境（範例：部分瀏覽器引擎）寫明「交由 CI」，不要寫成「全部通過」。
- 也執行「不允許略過」模式一次，確認它在仍有骨架時失敗（證明收尾的檢查會生效）。

---

## 7. 提交

- 先提交全部骨架，再逐項把骨架轉為實測，各自一個 commit；每個 commit 都讓編號檢查與全部測試通過。
- commit 訊息寫：依據的需求與設計章節、測試了什麼、變異檢查的方式與結果。
- 變更請求說明的作者段落列出測試 agent 的工作階段識別，與實作 agent 分開；測試段落列出本機結果與交由 CI 的環境。

- [ ] 沒有修改產品程式碼、檢查腳本或 CI 設定；發現的問題都已記錄並回報

**骨架**
- [ ] 必要編號清單已與設計的骨架計畫核對（數量與內容），不是只看檢查腳本的輸出
- [ ] 每個骨架名稱以編號開頭並摘要 Then；多範圍、多層的編號已分開命名
- [ ] 骨架的略過寫法被編號檢查判定為略過

**實際測試**
- [ ] Given／When 所需的畫面與操作都已存在；沒有自行加入捷徑
- [ ] 期望值來自需求或設計，不由受測程式產生
- [ ] 每個實際測試都做過變異檢查，且已還原
- [ ] 「證明沒有發生」的測試，先證明了有在運作
- [ ] 沒有重建或改動其他測試共用的輸出；沒有依賴 CI 未保證提供的環境變數
- [ ] 檢查腳本的驗收：本檔名稱不含其他必要編號；反例有對照組、在複本上做、刪除後語法合法、也以 CI 的指令確認結束代碼
- [ ] 每個反例只因目標規則失敗（斷言了行號與規則，其他部分合乎全部規則），並有同位置的對照組
- [ ] 以執行結果判定的檢查，已在最小暫存版本庫以 CI 的測試指令＋結果檢查指令跑過反例；巢狀執行器的內部環境變數已清除
- [ ] 斷言計數輔助：巢狀斷言只計一次、別名屬性與 Promise 斷言已處理、限制（並行、子測試）已寫明
- [ ] 檢查腳本的每條規則都做過變異，且有測試因此失敗；變異前已備份，結束後 `git status` 乾淨
- [ ] 設計變更造成的驗收測試修改，已在 commit 訊息寫明設計版本、章節與編號；從實作推得的邊界已列為假設

**執行與提交**
- [ ] 本機各層結果已記錄；未能執行的環境已註明交由 CI
- [ ] 每個 commit 都讓編號檢查通過；commit 訊息含依據與變異檢查
- [ ] 每個問題都依 agent-dev-workflow 第 7 節判斷過是否屬於 skill 的缺漏

## 9. 回饋機制

任何 agent 在測試、審查或系統測試時發現問題，依 agent-dev-workflow 第 7.3 節判斷是否為本 skill 的缺漏：

- 其他專案也可能發生、本 skill 沒有提醒 → 修改本 skill：加入規則，必要時加入第 5 節的範例與第 8 節的檢查項，範例去除專案細節。
- 本 skill 有規定但沒有照做 → 不改規則；若規定容易漏看，改寫得更明確。
- 只與某專案有關 → 記在該專案文件，不改本 skill。

修改方式依 agent-dev-workflow 第 7.4 節：在下方變更紀錄寫明日期、發現的階段、問題、修改內容（表格由舊到新，新版本加在**最後一列**：專案常以最後一列判定 skill 的最新版本號）；不得為了讓目前的工作通過而刪除或放寬檢查；修改後以新規則重新檢查目前產出。版本庫建立後，本 skill 的修改與程式碼一樣經過變更請求與審查。
