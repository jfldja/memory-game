# Agent 開發工作規範

本 skill 規範「怎麼開發」，不規範「開發什麼」。產品應有的行為一律以專案的需求文件為準。

**任何 agent 在開始設計、實作、測試、審查或修正程式之前，都先讀完本 skill，並完成第 1 節的上工檢查。**

---

## 0. 核心原則

1. **只依據已簽核的輸入工作。** 每個階段只依據上一階段已簽核或已通過的產出開始。
2. **不私下繞過。** 需求沒寫的行為不自行決定；驗收標準不為了讓工作通過而放寬；測試不為了讓程式通過而修改。
3. **寫程式的人不判定自己合格。** 撰寫程式碼的 agent，不撰寫判定該程式碼是否合格的驗收測試，也不審查自己的變更。
4. **問題回到源頭修。** 發現需求、設計、測試或程式有錯，回到負責的階段修正並升版，而不是在下游補丁。
5. **每個問題都問一次：這是 skill 的缺漏嗎？** 若是，修正 skill，讓下一個專案不再發生（見第 7 節）。
6. **無法判斷時停下來問。** 回報產品負責人，不要自行決定。

---

## 1. 上工檢查（每個 agent 開始工作前）

逐項確認，任一項不成立就停下來回報：

- [ ] 我知道自己在本次工作中的角色（第 3 節），以及這個角色「不負責」什麼。
- [ ] 我知道目前在哪個階段（第 4 節），以及這個階段的離開條件。
- [ ] 我的輸入文件都已簽核或已通過，且我讀的是最新版本。
- [ ] 我已讀過專案的需求文件。若專案沒有需求文件，先停下來：需求應依 requirements-spec skill 產出並由產品負責人簽核後，才能進入設計。
- [ ] 若專案有自己的工作規範文件（例如 `workflow.md`），我已讀過，並知道它對本 skill 做了哪些調整（第 2 節）。
- [ ] 我已載入本階段適用的其他 skill（例如設計、實作、測試階段的 skill）。

---

## 2. 文件的優先順序

一個專案通常有三類文件：需求文件、專案工作規範（選用）、本 skill。衝突時依下列順序：

1. **產品行為**：以需求文件為準。
2. **需求文件中已寫成需求的流程事項**（例如版本庫規則、CI、審查紀錄、驗收、發布）：以需求文件為準。工作規範與本 skill 只補充執行方式，不得放寬。
3. **其餘流程事項**：專案工作規範優先於本 skill。專案工作規範可以縮減或調整本 skill，但必須寫明調整了什麼、為什麼。
4. **無法判斷時**：停下來回報產品負責人。

閱讀規則：

- 工作規範與本 skill 的內容不是產品功能。不要把它們寫進規格書、程式碼或測試，也不要為它們在需求文件的追溯矩陣中建立編號。
- 需求文件若引用了外部 skill 的章節（例如「依 requirements-spec 第 3.8 節」），指的是該 skill，不是需求文件本身的章節。

## 3. 角色

| 角色 | 負責 | 不負責 |
|---|---|---|
| 產品負責人（人類） | 簽核需求與設計、執行使用者驗收（UAT）與標示為人工的驗收、發布、裁決需求變更 | 撰寫程式碼 |
| 統籌 agent | 分派工作、彙整結果、向產品負責人回報、維護需求文件 | 代替產品負責人簽核 |
| 設計 agent | 軟體規格書、模組劃分、各模組測試標準、其他設計產出 | 撰寫正式程式碼 |
| 實作 agent | 依設計撰寫程式碼與模組單元測試、開變更請求（Pull Request）、修正缺陷 | 審查自己的變更；為了讓測試通過而修改驗收測試 |
| 測試 agent | 撰寫並維護驗收測試、量測非功能需求、系統測試、測試報告、缺陷紀錄 | 修改產品程式碼以讓測試通過 |
| 審查 agent | 依審查清單審查每個變更（含實作 agent 與測試 agent 的），留下審查紀錄 | 修改被審查的內容；審查任何一位作者是自己的變更 |

### 3.1 測試分工

- **驗收測試**：直接對應需求文件驗收標準的自動化測試，由測試 agent 撰寫。不論以單元測試或端對端測試的形式實作，都屬驗收測試。若需求要求測試名稱包含驗收編號，依需求命名。
- **模組單元測試**：驗收標準以外、驗證模組內部行為的測試，由實作 agent 撰寫。

### 3.2 單一 agent 或資源有限時

環境不支援多個獨立 agent，或專案很小時，可以由同一個 agent 依序擔任多個角色，但必須維持下列獨立性：

- 撰寫驗收測試與撰寫程式碼分開進行：先依需求寫驗收測試，再寫程式碼；寫程式碼時不修改驗收測試。
- 審查在新的工作階段（全新的上下文）中進行，只讀變更內容、需求、設計與審查清單，不讀作者的推理過程。
- 在審查紀錄中誠實註明「審查者與作者為同一模型的不同工作階段」。
- 專案工作規範中寫明採用了這種縮減。

## 4. 階段、產出與交接

### 4.1 階段總覽

| 階段 | 執行者 | 輸入 | 產出 | 離開條件 |
|---|---|---|---|---|
| 1 需求 | 統籌 agent | 產品負責人的想法 | 需求文件（依 requirements-spec） | 產品負責人簽核 |
| 2 設計 | 設計 agent | 已簽核的需求文件 | 軟體規格書、模組測試標準、需求文件指派給設計階段的查證結果；設計 skill（若專案要求） | 產品負責人簽核 |
| 3 實作與測試 | 實作、測試、審查 agent 並行 | 已簽核的設計文件 | 程式碼、模組單元測試、驗收測試、變更請求、審查紀錄；實作 skill（若專案要求） | 見 4.3 |
| 4 系統測試 | 測試 agent | 主分支程式碼與部署版本 | 測試報告；測試 skill（若專案要求） | 見 4.4 |
| 5 使用者驗收 | 產品負責人 | 測試報告記載之 commit 的部署版本 | 驗收紀錄 | 全部通過；未通過依 5.2 |
| 6 發布 | 產品負責人 | 通過驗收的 commit | 版本標籤與發布說明 | 需求文件的發布條件完成 |

需求文件若有自己的里程碑，專案工作規範要寫出階段與里程碑的對應。

### 4.2 交接規則

- 每個階段結束時，向統籌 agent 交付：產出清單、尚未解決的問題、做過的假設、修改或建議修改的 skill（見 7.4）。
- 下游 agent 發現交付內容不足以開始工作時，依 5.1 回報，不自行補上猜測。

### 4.3 階段 3：實作與測試

實作 agent 與測試 agent 依同一份設計並行工作。

1. **建立基礎。** 第一批變更建立版本庫結構、CI、主分支保護規則，並提交先前階段已產出、應存放在版本庫的檔案（例如設計 skill）。
2. **逐項實作。** 每完成一項功能：
   - 實作 agent 提交程式碼與模組單元測試。
   - 測試 agent 提交對應的驗收測試，放在同一個變更請求，或在功能合併後的下一個變更請求。
3. **每個變更都經審查。** 審查 agent 不得是該變更的任何一位作者。
4. **不讓主分支壞掉。** 尚未實作之功能的驗收測試，不得在主分支上執行並失敗。

**驗收測試骨架（當 CI 要求「每個驗收編號都必須有對應測試」且「CI 必須通過才能合併」時）：**

這兩條規則同時存在時，逐項開發的每個變更都會因為其他編號尚無測試而被擋下。處理方式：

- 測試 agent 為每個要求的編號建立名稱含該編號、標記為「略過」的測試骨架。啟用編號檢查的那個變更，必須同時包含全部骨架。
- 每完成一項功能，把對應的骨架改為實際測試。**骨架轉為實際測試時，該驗收的 Given／When 所需的畫面、操作與資料，必須在同一個變更或更早的變更中已經存在。** 否則 CI 會失敗，或實作者只能自行加入規格沒有的進入方式。設計階段切分變更請求時，就要逐一檢查這點。
- 早期已轉為實際測試的驗收，在後續變更中仍須成立。改寫畫面或流程的變更，不得移除早期驗收所依賴的元素。
- 略過的測試名稱可以通過編號檢查，但**不算通過驗收**。

**啟動例外（依賴預設分支工作流程的檢查）：**

有些檢查只有在其工作流程已存在於預設分支後才會執行，例如由評論或審查事件觸發、再把結果寫回 commit 的檢查。這類檢查在「加入它的那個變更」合併之前不會生效，因此：

- 版本庫的初始 commit，以及加入這類檢查的第一批變更，必然不受這些檢查約束。這是無法避免的啟動例外，必須列為待決問題，由產品負責人在設計簽核時接受，並記錄在專案工作規範中。
- 第一批變更由產品負責人人工確認審查紀錄後合併。
- 分支保護中把這類檢查設為必要檢查的步驟，安排在它第一次實際執行之後（許多平台要求檢查至少執行過一次才能選取）。
- 啟動例外以外，不得再有不經檢查的合併。先前階段的產出（例如設計文件）隨第一批變更一起合併，不另外單獨合併。

**離開條件：**

- 需求文件中所有 Must 需求的自動化驗收，在主分支的 CI 通過。
- 驗收測試中沒有任何略過的測試。
- 需求文件要求的分支保護等規則已生效，標示為人工的部分由產品負責人確認。

### 4.4 階段 4：系統測試

測試 agent 對主分支最新 commit 及其部署版本執行：

1. 在需求文件要求的所有環境（瀏覽器、作業系統、裝置尺寸）執行全部自動化測試，確認與 CI 結果一致。
2. 依需求文件的狀態與操作對照（若有），逐格做探索式測試；沒有對照表時，依 requirements-spec 的狀態交互檢查方法自行列出主要組合。
3. 量測非功能需求並記錄結果。
4. 產出測試報告：受測的 commit 與版本號、每個驗收編號與非功能需求的結果、缺陷與其狀態、交由產品負責人確認的人工驗收清單。

**離開條件：**

- 測試報告中沒有未解決的 Must 缺陷。Should 以下的缺陷列在報告中，由產品負責人決定是否在本輪修正。
- 報告受測的 commit 是主分支最新 commit。期間若有合併，對最新 commit 重新執行步驟 1 與 3 並更新報告。

### 4.5 階段 5、6：使用者驗收與發布

- 驗收期間凍結主分支，不合併任何變更。
- 發布的版本必須是通過驗收的那個 commit。驗收後主分支若有變更，重新驗收。

## 5. 發現問題時

### 5.1 上游文件有問題

1. **不要私下繞過。** 不在程式碼或測試中自行決定需求沒寫的行為。
2. **記錄問題。** 哪份文件、哪個編號、問題是什麼、在什麼情境下發現、建議改法。
3. **回到負責的階段處理。**
   - 需求文件：統籌 agent 依 requirements-spec 修訂，產品負責人核准後升版。
   - 設計文件：設計 agent 修訂，產品負責人核准後升版。
4. **檢查下游影響。** 升版後，統籌 agent 列出受影響的設計章節、程式碼與測試，交給對應的 agent 修正。
5. **檢查是否屬於 skill 的缺漏**（見第 7 節）。

### 5.2 程式缺陷

1. **判斷錯在哪裡**，以需求文件為準：
   - 程式不符需求 → 程式缺陷，進入步驟 2。
   - 測試與需求不符 → 測試 agent 修正測試，經審查後合併。修改理由寫在變更請求中並引用需求編號。
   - 需求本身不清楚或矛盾 → 依 5.1。
2. **記錄缺陷**：對應的需求或驗收編號、重現步驟、預期結果、實際結果、受測的 commit、優先級（依對應需求）。
3. **修正**：實作 agent 開變更請求，依一般流程審查與合併。
4. **驗證**：測試 agent 確認原本失敗的測試通過，並以全部自動化測試確認沒有退化。缺陷若沒有被任何現有測試發現，補上能重現它的測試。
5. **回到原階段**：
   - 階段 3、4 發現：修正後繼續原階段。
   - 使用者驗收發現：回到階段 3 修正，重新完成階段 4，再重新執行全部驗收項目。
6. **檢查是否屬於 skill 的缺漏**（見第 7 節）。

## 6. 專案工作規範（選用）

專案需要調整本 skill 時（例如縮減階段、合併角色、對應里程碑、規定 skill 存放位置），在版本庫或專案文件中建立 `workflow.md`，內容至少包含：

- 階段與需求文件里程碑的對應。
- 對本 skill 的調整，以及每項調整的理由。
- 本專案要產出哪些可重用 skill、存放在哪裡、何時提交。
- 給產品負責人的已知事項：本規範發現、但屬於需求文件範圍而未修改的問題。
- 完成條件與變更紀錄。

專案工作規範不是產品需求，不在需求文件的驗收與追溯範圍內。

---

## 7. 可重用 skill 與回饋修正

### 7.1 何時產出 skill

專案要求時，每個階段的 agent 在完成工作的過程中，撰寫該階段的可重用 skill。存放位置與提交時點依專案工作規範；版本庫建立前產出的 skill，先隨該階段產出交付產品負責人，版本庫建立後再提交。版本庫建立後，對 skill 的修改與程式碼一樣經過變更請求與審查。

### 7.2 skill 的撰寫規則

- **與專案無關。** 必須能用在下一個專案。不得把特定專案的規則、數值、檔名寫成內容；需要舉例時，明確標示為範例。
- **說明輸入與產出。** 需要上一階段提供什麼，交付給下一階段什麼。
- **貼近業界做法。** 依循常見實務（設計審查、測試金字塔、程式碼審查、持續整合），並說明在單人或小型專案中如何縮減。
- **附自我審查清單。** 交付前逐項檢查的清單。
- **包含回饋機制。** 有一節說明如何依本 skill 第 7.3、7.4 節修正該 skill，以及變更紀錄。

### 7.3 判斷是否修改 skill

任何 agent 發現問題時（含第 5 節的情況），除了修正產出，還要判斷根源是否為 skill 的缺漏：

| 情況 | 處理 |
|---|---|
| 這類問題在其他專案也可能發生，而 skill 沒有提醒或檢查 | 修改 skill |
| skill 有規定，但執行時沒有照做 | 不改 skill，修正產出；若規定寫得容易漏看，改寫得更明確 |
| 只與本專案的特殊條件有關 | 不改 skill，記在專案文件中 |

### 7.4 修改方式

1. 加入能預防這類問題的規則，視需要加入審查清單項目與「錯誤寫法／改寫」範例。範例去除專案細節，改寫成通用情境。
2. 在 skill 的變更紀錄寫明：日期、發現的階段、問題、修改內容。
3. 不得為了讓目前的工作通過而刪除或放寬 skill 中的檢查。
4. 修改後，用新規則重新檢查目前階段的產出；同類問題若可能存在於已完成階段的產出，回報統籌 agent。
5. 由產品負責人安裝與維護、agent 無法直接修改的 skill（包括本 skill 與 requirements-spec），寫出建議的修改段落，交給產品負責人決定。
6. 每次修改或建議修改，都列在該階段的交付摘要中。

## 8. 交付前自我審查清單

**輸入與角色**
- [ ] 完成了第 1 節的上工檢查
- [ ] 沒有做角色表中「不負責」的事

**獨立性**
- [ ] 沒有為了讓測試通過而修改驗收測試或放寬驗收標準
- [ ] 沒有審查任何一位作者是自己的變更
- [ ] 單一 agent 分飾多角時，已依 3.2 維持獨立並在紀錄中註明

**需求一致性**
- [ ] 沒有實作需求文件沒有寫的行為；遇到空白時已依 5.1 回報
- [ ] 每個變更都能對應到需求或設計的編號

**主分支與版本**
- [ ] 主分支的 CI 沒有因為本次變更而失敗
- [ ] 沒有在主分支上留下會失敗的未實作驗收測試
