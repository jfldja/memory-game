# 設計階段 Skill

本 skill 規範「如何把已簽核的需求變成可實作、可驗收的設計」。它與專案無關；文中出現的具體數值或名稱都標示為「範例」。

搭配使用：開發流程與角色依 `agent-dev-workflow`；狀態交互檢查方法依 `requirements-spec` 第 3.8 節。

---

## 0. 核心原則

1. **需求是唯一依據。** 設計只決定「怎麼做」。需求沒有規定的行為不在設計中自行決定，列為待決問題交產品負責人。
2. **可測性是設計的一部分。** 時間、亂數、儲存、網路等外部依賴一律可注入；邏輯與畫面分離；驗收標準提到的每個觀察點，設計都要提供穩定的讀取方式。
3. **每條 Must 需求都有去處。** 對應到設計章節、模組與測試層；追溯表用腳本核對，不靠目測。
4. **查證寫原文與網址。** 平台限制、免費額度、權限行為，引用官方文件原文；讀不到就寫「未查證」，並安排實測。
5. **設計流程本身也會卡住開發。** CI 規則之間的交互（例如「每個編號要有測試」＋「CI 全過才能合併」）要在設計時解掉。

---

## 1. 輸入與產出

**輸入（缺任何一項就停下來回報）：**

- 已簽核的需求文件（含驗收標準、非功能需求、限制、待決問題、追溯矩陣）。
- 專案工作規範（若有）。
- 需求指派給設計階段的查證項目與期限。

**產出（交付統籌 agent，再由產品負責人簽核）：**

| 產出 | 內容 |
|---|---|
| 查證紀錄 | 每個指派的查證問題：結論、官方原文節錄、網址、查證狀態（已查證／實測／未查證）、對需求的影響 |
| 軟體規格書 | 架構與相依方向、檔案結構、模組介面（函式簽名、資料格式、事件）、狀態機、計時設計、外部依賴的抽象、儲存格式、畫面元素與版面計算、建置與版本、CI／CD、PR 切分、待決問題、假設、變更紀錄 |
| 模組測試標準 | 每個模組要測的行為、邊界、對應需求與驗收編號、單元測試與驗收測試的分界；Must 需求追溯表 |
| 驗收測試骨架計畫 | 所有要求自動測試的編號、所屬測試層、骨架位置、轉為實測的 PR |
| 審查流程 | 審查紀錄格式、審查清單、自動檢查的判定規則 |
| 其他需求指定的設計產出 | 範例：圖像草稿與屬性表 |
| 簽核欄 | 讓產品負責人留下簽核日期與版本 |

## 2. 步驟

1. **上工檢查。** 依 agent-dev-workflow 第 1 節。讀完需求全文，特別是術語表、狀態與操作對照（若有）、限制、設計候選方案、驗收標準、待決問題。
2. **先做查證。** 指派給設計階段的查證問題先處理，因為結論可能推翻架構（例如平台不免費、某事件不會觸發檢查）。見第 5.1 節。
3. **劃分模組。** 依第 4 節的可測性原則，先切出「純邏輯」與「平台包裝」與「畫面」，寫出相依方向。
4. **設計狀態機。** 依第 3 節。逐格對照需求的狀態表；需求沒有狀態表時，自己依 requirements-spec 3.8 列出。
5. **設計計時、亂數、儲存。** 依第 4 節。
6. **設計畫面。** 元素清單、每個需求觀察點的 DOM 測試介面、版面尺寸計算（寫出算式與每個要求尺寸的結果）。
7. **設計 CI、審查、部署。** 依第 5 節。
8. **規劃驗收骨架與 PR 切分。** 依第 6 節。
9. **寫模組測試標準與追溯表。** 以腳本核對追溯表與需求矩陣的 Must 集合相同。
10. **自我審查**（第 9 節），交付。

## 3. 狀態機與計時器設計檢查

### 3.1 先定狀態變數，再推導狀態

把狀態拆成**正交的變數**（範例：`phase`、`paused`、`firstSelection`、`lock`、`highlight`），用條件組合推導出需求中的狀態名稱。這樣「暫停」可以疊在任何進行中狀態上，不必為每個組合各寫一個狀態。

### 3.2 寫出轉移表

每條轉移：代號、觸發、守衛（全部成立才執行）、效果、對應需求編號。另寫一條「其他情況：無效果」，列出每個守衛不成立的原因與對應需求。

### 3.3 逐格對照

- **狀態 × 操作：** 每格寫出轉移代號與需求編號。需求有對照表時逐格比對，不一致即為設計錯誤或需求矛盾。
- **狀態 × 計時器：** 每個計時器在每個狀態下是繼續、暫停、取消還是不存在。
- **邊界：** 「只剩最後一個」「第一次」「剛好在上限」「計時器到期與操作同一時刻」「同一操作連按兩次」「暫停中切到背景」「多個分頁」「重新整理」。
- **同時到期的順序：** 寫明處理順序與理由，並確認結果符合需求（範例：點擊時刻等於時間上限時先判定失敗）。
- **不變式：** 寫出幾條任何操作後都必須成立的條件，交給單元測試檢查。每條不變式寫明**適用的狀態**；寫完後逐條拿去對照每個終止或取消轉移（範例：時間到時取消鎖定，翻開的牌仍維持正面），確認轉移的結果不違反不變式。

### 3.4 需求沒寫的組合

寫成待決問題：問題、發現情境、選項（各自的影響與成本）、建議、阻擋哪個 PR。**不要**在規格書裡「先選一個」而不標示，也**不要寫成「假設」**：假設的預設立場是「已接受」，等於代替產品負責人決定。受影響的設計處標示「依 DQ-n 決定」，決定前不得實作任一選項。只影響 Should 需求的，安排在較後面的 PR，讓決定不阻擋 Must。

特別容易被誤當成「技術細節」的產品決定：

- 為了可測性而暴露的資訊（範例：DOM 屬性或可及性名稱帶有答案、測試用網址參數）。依 requirements-spec 3.8「會不會讓使用者取得不該有的資訊」判斷。
- 流程需求的例外（範例：「只能透過 PR 變更」在版本庫啟動時必然有的直接推送）。
- 外部服務的上限等於需求期限、沒有餘裕時的處理方式。
- 「整份作廢」這類錯誤處理的連帶影響（範例：資料格式不符時整份視為無效，下一次寫入會覆蓋其他仍有效的部分）。
- Should 需求的本輪範圍（影響驗收骨架與編號檢查在哪個 PR 啟用）。

### 3.4.1 待決問題關閉後

產品負責人決定後，設計 agent 修訂設計並升版，不只在待決問題表上打勾：

1. **替換全部標示。** 以腳本搜尋「依 DQ-n 決定」等標示，逐處改寫為決定後的設計；搜尋結果只能剩下歷史紀錄（變更紀錄、修訂紀錄）。待決問題表改為「已關閉」，記錄決定內容、決定者與日期、寫入的章節。
1a. **選項摘要不等於規則；決定紀錄與正文改寫放在同一個 commit。** 待決問題表的選項欄通常只有一句摘要（範例：「擴大偵測：移除 HTML 與跳脫後，去除行首非字母數字字元」），實作者無法只憑它寫出程式。決定後，把被採用的選項展開成完整規則寫進正文：步驟順序、哪些步驟重複到不動點、每一步的確切字元或模式範圍、邊界案例的判定表（含「仍維持原判定」的案例與理由），以及對合法範本與實際資料的回歸檢查；同時刪除「決定前維持本段」「決定前不實作」等過渡句。記錄決定的角色與設計 agent 不同時（範例：統籌 agent 代記產品負責人的決定），設計 agent 在決定紀錄之後的第一個 commit 完成改寫；改寫前，下游以「正文仍是決定前的寫法」為由停下回報是正確的做法。另以腳本搜尋「待決定」「待確認」等狀態字樣，表頭、章節標題、說明段落與簽核欄須一致。
2. **需要改需求的決定，等需求升版後再引用。** 由負責需求的角色修訂並升版（agent-dev-workflow 5.1），設計文件的依據改為新版本；設計不得在需求升版前先寫成新行為。
3. **補驗收的正例與反例。** 決定新增或改變了條件（範例：「尚無既有值時也標示」），補充驗收要同時涵蓋：條件成立的每種來源（範例：從未有值、單一項目為空、資料整份作廢後為空）與不成立的鄰近情況（範例：其他範圍為空但本範圍有值、第一次之後的第二次）。
4. **檢查決定之間的交互。** 兩個以上的決定作用在同一份資料或同一個畫面時（範例：「格式不符整份作廢」×「無既有值時標示」×「儲存不可用時只存在記憶體」），逐對寫出組合結果並確認一致。
5. **過渡規則寫明結束條件。** 決定含「在某外部事件之前暫用某規則」時（範例：等待另一個 PR 同步檔案），寫明結束事件、結束後的行為、由誰觸發，以及規則本身是否需要修改。結束事件實際以不同方式發生時（範例：預定的獨立 PR 改為併入另一個 PR），下一次修訂時搜尋並改寫所有描述該事件的段落，不留下「將由另一個 PR」這類過時說法。
6. **重查 PR 切分。** 決定新增的程式或測試輔助所依賴的模組，必須在該 PR 或更早存在（第 6 節）。
7. 依第 9 節重新自我審查，並以腳本重新核對追溯與骨架清單。

### 3.5 計時器設計

- **單一時間來源。** 經過時間用單調時鐘相減（範例：`performance.now()`），不累加計時器間隔。
- **共用遊戲時鐘。** 會隨暫停一起停止的倒數（範例：鎖定、標示），用同一個「扣除暫停的時鐘」計算到期時刻，就不必個別保存剩餘時間。
- **以截止時間排程，不用固定影格。** 邏輯回報「下一個需要更新的時刻」（下一個顯示值邊界、各倒數到期、上限），外層只排一個計時器。固定影格（約 16 ms）會讓顯示值在邊界時刻落後一格，驗收檢查點會因此失敗。
- **顯示值與內部值一致。** 若需求以顯示值判定（範例：無條件捨去到 0.1 秒），判定與保存一律用整數化的顯示值；整數化前先處理浮點誤差（範例：先四捨五入到微秒）。轉移守衛也要寫成「顯示值 ≥ 上限」，不要寫成原始值比較再聲稱兩者等價：只要有任何前處理（四捨五入），兩者就在極小的區間內不同。排程喚醒可以用原始時刻，到期時以顯示值判定。
- **背景分頁。** 瀏覽器會降頻計時器；以單調時鐘相減時，回到前景的第一次喚醒補做到期事件即可。需求要求自動暫停時，用 `visibilitychange`。

## 4. 可測性設計

| 依賴 | 做法 | 測試方式 |
|---|---|---|
| 時間 | 邏輯函式以參數接收 `now`；平台層只有 `now()` 與 `setTimer(at, cb)` 兩個入口 | 單元測試直接傳數字；端對端用瀏覽器測試工具的時鐘控制 |
| 「必須用真實時間」的量測 | 不控制時鐘的獨立測試，量測方法寫在測試計畫 | 以「指令前後兩個時間戳」夾出實際經過時間的區間，再與顯示值比較 |
| 亂數 | 注入 `randomInt(n)`；正式實作用密碼學亂數並以拒絕取樣消除取模偏差 | 單元測試注入固定序列；統計型驗收在無瀏覽器環境呼叫與正式程式相同的函式 |
| 儲存 | 平台包裝吞掉所有例外，回傳狀態；資料格式含版本欄位 | 注入假的 storage；端對端用初始化腳本預寫資料 |
| 畫面 | 邏輯回傳唯讀快照，畫面只依快照繪製 | 端對端依「DOM 測試介面表」操作 |
| 建置資訊 | 版本號在建置時寫入常數模組，執行時不載入任何東西 | 以環境變數指定 commit 建置後檢查 |

**DOM 測試介面表。** 把端對端測試會用到的選擇器、屬性與文字格式寫成一張表，屬於介面，變更要同步修改測試並經審查。數值元素只放數值，單位放相鄰元素。

**檢查腳本的純函式介面要逐條對照規則。** 規格寫出判定函式的簽名時，逐條判定規則列出它讀到的資料，確認每一項都在參數中（範例：「每個測試檔至少有一筆結果」需要檔案清單，不能只有測試名稱清單；「必要編號都有通過的結果」需要必要編號清單；「執行器的全域錯誤即失敗」需要錯誤清單）。外層包裝的特殊模式（範例：只讀的試算模式）在一般模式會提早結束的狀態下（範例：對象已關閉）怎麼做，也要寫明。否則實作者只能自行補參數與行為。

**停用狀態的表示。** 若需求的「無法使用」是「可見、點擊無效果、不被遮蔽」，用 `aria-disabled` 並在處理器中忽略，不用 `disabled` 屬性；並告訴測試：多數瀏覽器測試工具把兩者都視為不可點擊，要以座標點擊驗證「無效果」。

**邏輯狀態與實際渲染分開暴露。** 元素的邏輯狀態與畫面上實際呈現的內容可能不同（範例：遊戲中一張牌邏輯上是「正面」，但暫停遮蔽時實際畫的是背面）。驗收要判斷「看不到」「顯示的是什麼」時，介面表就要有「實際渲染內容」的屬性（範例：`data-shown`），不能讓測試去解析圖像內部結構。

**不讓測試介面洩漏使用者不該取得的資訊。** DOM 屬性、圖像與可及性名稱不得帶有使用者在該狀態下不該知道的資訊（範例：遊戲的答案、未公開的內容）；測試需要的隱藏資訊改用注入（例如以初始化腳本控制或記錄亂數，在測試端用同一個純函式重算）。真的必須暴露時，列為待決問題（3.4）。

**以記錄的亂數重放時，定義錨點與契約。** 記錄的是整個頁面期間的全部亂數輸出，其中混有多個消耗者（範例：發牌、提示選牌、拒絕取樣的重抽）。不要假設「每次固定取 N 個值」：規定測試在觸發目標運算的操作之前讀取記錄長度作為錨點，並在規格中寫明契約（每次抽取呼叫幾次底層亂數、該操作處理器中第一個消耗亂數的是目標運算），由單元測試固定。重放用正式程式的同一個函式；記錄不足視為測試錯誤，不得補值。

**不要用 `overflow: hidden` 掩蓋版面溢出**，否則「無捲動」的驗收失去意義。

**版面算式的常數必須是實作會寫的 CSS。** 每個高度、行高、間距都以固定值寫進規格（範例：狀態列 `height: 52px`、文字 `line-height: 20px`、`white-space: nowrap`），不得依賴字型的預設行高（中日韓系統字型的 `line-height: normal` 常在 1.4～1.5）。表格列出每個要求尺寸的**餘裕**，並訂出最小餘裕（範例：4 px；依專案的取整方式與目標瀏覽器差異訂定），低於最小餘裕視為不成立。可點擊尺寸的下限也留餘裕（範例：要求 44 px 時用 48 px）。

**真實時間量測的判定不得放寬。** 以「指令前後兩個時間戳」夾出實際值區間 [lo, hi] 時，判定要求區間兩端都在容差內（`|d − lo| ≤ 容差` 且 `|d − hi| ≤ 容差`），不得以「d 與區間的距離 ≤ 容差」判定。兩端判定本身已不比需求寬鬆，不需再設區間寬度上限（多設會把量測工具的往返延遲誤判為計時錯誤）；區間寬度只記錄供診斷，並以縮短往返的操作方式（範例：座標點擊、單一次讀值）讓區間變窄。長時間量測要覆寫逾時，並與其他測試隔離（獨立 project、單一 worker），避免負載影響計時器。

## 5. CI／審查流程設計

### 5.1 查證平台事實

對每個流程需求列出所依賴的平台行為，逐項查官方文件。範例（GitHub）：公開版本庫的 Actions 與 Pages 是否免費、分支保護預設是否約束管理員、必要檢查可否是 commit status、哪些事件會觸發工作流程、事件中的 commit SHA 是哪一個、部署延遲上限。

### 5.2 已知陷阱（GitHub，其他平台檢查同類問題）

| 陷阱 | 後果 | 做法 |
|---|---|---|
| PR 評論不會重新觸發掛在 commit 上的 CI 檢查；`issue_comment` 事件在**預設分支**的情境執行，job 結果不會掛在 PR 的 commit 上 | 「有審查紀錄才能合併」的檢查永遠不會因為留了紀錄而變綠 | 評論事件觸發的工作流程以 API **重新讀取** PR 最新 head SHA，判定後以 commit status 寫回該 SHA；推送事件同樣寫入。新 commit 沒有舊狀態，自然回到未通過 |
| `issue_comment`、`pull_request_target` 只執行預設分支上的工作流程檔 | 加入這個檢查的第一個 PR 無法被它把關 | 規格書寫明「啟動例外」：第一個 PR 由人工確認後合併，再啟用分支保護；驗收在之後的 PR 執行 |
| `pull_request_target` 有寫入權限 | 簽出並執行 PR 程式碼會外洩權限 | 只執行預設分支上的判定腳本，不簽出 PR 程式碼 |
| 公開版本庫任何人都能評論 | 偽造審查紀錄 | 只採計 `author_association` 為擁有者、成員、協作者的評論 |
| 分支保護預設不約束管理員 | 單人專案可直接繞過 | 勾選「不允許繞過」的設定；寫進手動設定步驟 |
| `pull_request` 事件的 `GITHUB_SHA` 是合併 commit，不是 PR 的 commit | 版本號或狀態對不上 PR | 用事件內容中 PR 的 head SHA |
| 以 `GITHUB_TOKEN` 觸發的事件不會建立新的工作流程執行 | 自動化之間無法串接 | 需要串接時改用可串接的事件，或在同一個工作流程內完成 |
| 必要檢查名稱要先執行過才選得到 | 第一個 PR 前無法設定保護 | 設定步驟排在第一次 CI 執行之後 |
| 官方部署延遲上限等於需求的期限 | 驗收沒有餘裕 | 部署不等待重複的測試；部署後輪詢公開網址並在期限前判定，作為證據；超過時的處理方式列為待決問題交產品負責人 |
| 在 `run:` 中以 `${{ }}` 插值評論內容、PR 標題或說明、分支名稱 | 指令注入；在有寫入權限的事件中尤其危險 | 只以 `env:` 傳數字型欄位，其餘由腳本經 API 或事件檔讀取 |
| 同一 PR 的評論新增、編輯、刪除幾乎同時發生 | 較晚完成的舊執行以過時判定覆寫狀態 | 並行群組以 PR 編號為鍵（各事件取編號的欄位不同，要分別寫）、不取消進行中的執行、每次重新讀取最新狀態 |
| 只靠 commit status 的必要檢查，在加入它的 PR 期間不會執行 | 合併該 PR 後仍選不到這個檢查名稱 | 分兩段設定：先設定其餘必要檢查，下一個 PR 寫入過一次狀態後、合併前再加入。「下一個 PR」指加入後的**第一個** PR，不論內容；之後在中間插入新的 PR 時，設定步驟與對應驗收跟著移到插入的 PR，否則插入的 PR 會成為未經檢查的合併。該檢查在預設分支上從未執行過，第一次執行可能無法寫入狀態：寫出此時的處理方式（通常是再一個啟動例外），列為待決問題 |
| 修正「只在預設分支生效」的檢查本身（範例：修正審查紀錄的判定漏洞） | 該 PR 由預設分支上**修正前**的版本判定，修正在合併後才生效；新版在合併後才第一次在平台上執行，驗收證據描述的是已被取代的版本 | 規格寫明這個限制；以新版判定函式對該 PR 的實際資料試算（只讀不寫，範例：`--dry-run`）取代或補足人工確認，人工確認清單逐項列出新舊版本的每個差異；合併後的第一個 PR 重新觀察該檢查的驗收，作為描述主分支版本的證據，之後每次修改該檢查都重做。任何時候預設分支上的版本無法運作（第一次執行或之後的版本），修正它的 PR 都屬啟動例外，列為待決問題；可先開一個不合併的探測 PR 觸發第一次執行，把失敗風險移到不需要合併的 PR 上。**連續修正**（範例：修正合併後，其審查又發現同一檢查的漏洞）：中間版本可以不做合併後的觀察，最後版本合併後只開一次探測 PR；但每個修正 PR 本身都是前一個版本在平台上的第一次執行，前一版無法運作時同樣屬啟動例外，規格要寫明這個代價與處理方式。被檢查匯入的模組（範例：檢查腳本匯入另一支檢查的解析函式）的修改，也算修改該檢查。修正 PR 的審查紀錄要同時通過舊版（寫入狀態）與新版（試算）；收緊後會被拒絕的寫法（範例：描述漏洞時照寫被禁止的字元）要在規格中提醒審查者改以文字描述 |
| 建置用的環境變數（範例：commit SHA）只設在建置步驟 | 驗證版本號的測試步驟拿不到預期值，只能檢查格式，CI 中沒有任何檢查確認受測建置對應正確的 commit | 在 job 層級設定，建置與測試讀同一個值；測試在 CI 中缺少該值時失敗，不得退回只檢查格式 |
| 開第一個 PR 需要基底分支 | 初始 commit 必然直接推送，違反「只能透過 PR 變更」 | 寫成啟動例外，列為待決問題由產品負責人接受 |
| `pull_request` 事件以 PR 自己的版本執行工作流程與檢查腳本 | PR 可以修改自己的檢查讓自己通過 | 審查清單加一項：修改 CI、檢查腳本、驗收啟用設定或需求文件的 PR，審查者確認沒有降低任何檢查 |
| `node --test` 傳入目錄（Node.js 21 起位置參數視為 glob） | 「Cannot find module」，測試全部失敗（範例：Node.js 22 實測） | 以引號傳入 glob，例如 `'tests/unit/**/*.test.mjs'`，並在第一個 PR 實測 |

### 5.3 審查紀錄與審查檢查

- 紀錄格式含：可解析的標記行、結果、**完整** commit SHA、審查者與作者的工作階段識別、獨立性註明（同一模型不同工作階段時要明寫）、審查依據版本、逐項結果。
- 審查清單第一項固定為「作者是否證明讀過規範」（範例：PR 說明含上工檢查與 skill 版本號）。
- 自動判定寫成純函式，邊界列入模組測試標準：無紀錄、舊 SHA、短 SHA、非協作者、審查者等於作者、清單缺項、「不通過」卻寫核准、多則以最後一則為準。
- **同一則紀錄內的矛盾與寫法差異也要規定，判定採白名單。** 解析時以「項目編號 → 結果」的對應表保存，同一項目重複出現時後一列會覆蓋前一列，「不通過」可被同編號的「通過」蓋掉；只採計「看起來正確」的列時，寫成粗體、全形或加註的列會被忽略，其中的「不通過」同樣被蓋掉。規定紀錄的**唯一**合法格式，任何一處不符即整則無效、不嘗試解讀：不可見格式字元；標頭欄位（範例：結果、針對的 commit、審查者）各恰好一行，重複即無效；只允許一個逐項表格，每一列的第一格逐字符合項目編號格式，同一項目恰好一列、不得有清單以外的項目；結果欄只接受固定的幾個值；任一列不通過即不通過。最後一則紀錄無效時不退回採用較早的紀錄。識別碼（範例：工作階段、帳號）由人或 agent 自行填寫時，先去除空白、做 Unicode 正規化（全形轉半形）並統一大小寫再比對，**並限定正規化後的字元集**（範例：`^[a-z0-9-]+$`），因為 Unicode 正規化不會移除零寬字元，也不會把相似字轉成拉丁字母。這些情況列入模組測試的邊界。
- **偵測「看似某欄位的行」的正規化，先拿合法範本驗證。** 白名單要先找出所有「看似某欄位」的行，才能判斷「恰好一行」。偵測用的正規化若沒有去除合法格式本身帶的標記（範例：合法行以清單符號 `- ` 開頭，偵測卻要求去除空白後以欄位名稱開頭），**合法行本身就偵測不到**：依字面實作時每一則紀錄都無效；若實作者改為只採計逐字格式的行，重複偵測就失效。做法：偵測以標記語言渲染後讀者看到的文字開頭為準，去除行首的區塊標記（範例：Markdown 的引用、清單、有序清單、標題），合法與否仍以原文逐字比對；寫完規則後，把合法範本與每個反例逐行跑一次偵測，在規格中寫出每一行的偵測結果。擴大偵測只會增加無效的情況，不會讓任何行從判定中消失；仍不涵蓋的寫法（範例：正規化不轉換的項目符號、HTML、跳脫字元）實測後列為殘餘風險，是否再收緊列為待決問題。
- **渲染器在原文與讀者之間做的轉換，逐類列出並以真實渲染器實測。** 逐行去除行首符號只處理「同一行內、字面可見」的差異。標記語言的渲染器另有幾類轉換，逐行的偵測看不到：(1) **跨行的區塊範圍**（範例：GFM 表格延續到空行為止，緊接在表格後、沒有直線的行也成為一列；只有冒號與連字號的分隔列構成單欄表格；HTML 標籤可以跨行）；(2) **解碼**（範例：字元參照 `&#x…;`、具名參照）；(3) **不可見但不屬於格式字元類別的字元**（範例：Unicode 的 Default_Ignorable_Code_Point 中屬於字母或結合符號者、顯示為空白的字母或符號、結合符號）；(4) **隱藏**（範例：HTML 註解、處理指令）。每一類都檢查**兩個方向**：讀者看得到、檢查偵測不到（第二個欄位或第二個表格列）；檢查讀得到、讀者看不到（合法欄位行、整個表格或必要的註明藏在註解中）。每一類選擇「模擬」或「拒絕」：合法格式用不到的構造（字元參照、註解、可忽略字元）優先整則拒絕，比模擬渲染器便宜且沒有遺漏；表格範圍這類必須存在的構造，寫成可機械判定的邊界規則（範例：表格後必須是空行；全文只能有一個分隔列，分隔列的偵測是所有容器中分隔列寫法的超集）。結論不要只依規格推定：以平台實際使用的渲染器（範例：平台的開源渲染程式庫、平台 API 回傳的渲染結果）逐案實測，把「寫法、渲染後讀者看到什麼、現行判定、收緊後判定」寫成表，作為模組單元測試的資料；再以合法範本與實際紀錄跑一次收緊後的規則，把會被誤判的寫法寫進選項的影響。
- **「只增加無效」以構造保證，不以論證保證。** 收緊時若**取代**了舊的偵測步驟（範例：把標籤的正規表示式換成更精確的文法），新偵測可能在某些輸入上偵測得比舊的少：正規化前後判定位置不同（範例：一條規則看原文、另一條看相容正規化之後，全形符號在正規化後才成為語法字元），或更精確的文法把舊版留下的文字整段刪掉（範例：引號中的 `>`）。做法：「看似某欄位」「看似表格列」等偵測一律取**新偵測 ∪ 修改前偵測**，修改前的偵測逐字保留為相容基準；再以差分測試驗證「新版有效 ⇒ 舊版有效」：輸入涵蓋所有正規化會改變、且結果為語法字元或英數的碼位（以程式列舉，不手選），舊版以固定的複本作為對照。
- 誠實寫出殘餘風險：自動檢查只能證明紀錄存在，不能證明審查做過。

### 5.4 手動設定清單

平台網頁上只能由人設定的項目（公開、部署來源、分支保護、環境保護），寫成有順序、有時點的步驟表，標明執行者。

## 6. 驗收測試骨架與 PR 切分

- 從需求逐一列出要求自動測試的編號（含「自動＋人工」與要求自動量測的非功能需求），扣除需求明文的例外。**用腳本解析需求文件核對數量**，不要手數。
- 每個編號指定測試層：能在無瀏覽器環境判定的放下層（快、確定）；畫面觀察點放端對端層。同一編號可兩層都有。
- 啟用編號檢查的那個 PR 必須同時包含全部骨架（agent-dev-workflow 4.3）。編號檢查要能分辨「略過」，並在階段離開前打開「不允許略過」。
- 編號比對要以完整編號比對（範例：`AC-X-1` 不得被 `AC-X-10` 誤判），只採計測試名稱字串，不採計註解。
- **採計覆蓋的範圍只含驗收測試。** 編號檢查若掃描整個測試目錄，實作者撰寫的模組單元測試只要名稱含驗收編號，就會被算成驗收覆蓋，等於讓寫程式的人判定自己合格。規定：只掃描驗收測試目錄；另外檢查單元測試名稱**不得**含必要編號（失敗並列出位置），讓冒充與誤命名在變更請求中就被發現。縮小覆蓋範圍時，不得順帶取消原本對其他目錄的略過檢查。
- **掃描到的測試必須是會被執行的測試。** 規定驗收測試檔的位置與副檔名必須落在執行器實際執行的範圍（範例：單元層的 glob、端對端工具的測試目錄）；不符的檔案判定失敗。否則靜態掃描看得到、執行器卻不執行，編號檢查通過而驗收從未跑過。
- **略過的判定以執行結果為準，靜態偵測只是第一道。** 靜態掃描能涵蓋宣告形式（範例：`test.skip(名稱, …)`、`describe.skip`、`{ skip }`），但涵蓋不了測試本體內的執行期呼叫（範例：`test.skip()`、`test.skip(條件)`、`t.skip()`、`testInfo.skip()`）、註記選項、預期失敗（範例：`test.fail()`）、別名與動態屬性。做法：
  1. 驗收測試只允許**一種**略過寫法（骨架宣告），其餘寫法由靜態檢查一律判定失敗，並寫出偵測規則（範例：名稱為 `skip`、`fixme`、`fail`、`todo`、`only` 的屬性存取、計算屬性與物件鍵；列出必要的例外，例如斷言庫的 `assert.fail`）。
  2. 以測試執行器的**結果**判定：每個驗收測試都有執行結果、預期狀態是「通過」、實際結果是「通過」；略過只在對應到骨架宣告時暫時允許，收尾時一律不允許。逐引擎判定，不要合併後才判定。
  3. 讀結果時注意格式陷阱（範例，一個端對端工具的實測）：預期失敗的測試被算在「符合預期」而不是「略過」，只看略過統計會漏掉；略過區塊內的測試在部分執行器的結果中完全不出現，要以靜態清單比對「有沒有執行」；內建報表格式可能沒有檔名，需要自訂輸出。
  4. 在設計時本機實測一次每種寫法在結果中的樣子，寫進查證紀錄。
- **結果檔是兩個步驟之間的介面，交接方式寫成契約。** 以執行結果判定時，規定：(1) 結果檔的位置，且不放在工具每次執行會清空的目錄（範例：一個端對端工具的輸出目錄在每次執行開始時清空，同一 job 的兩次執行會互相刪除）；(2) 完整性標記（範例：最後一行為結束標記並帶筆數），缺少、筆數不符或格式錯誤時以「輸入錯誤」失敗，與判定失敗區分，讓「執行中途中止的部分結果」不會被當成「完整但測試較少」；(3) 寫入前先清空，避免讀到上一次的結果；(4) 同一 job 多次執行時各自的檔名與指定方式（範例：環境變數），以及設定被移除時是失敗而不是靜默少檢查一次執行；(5) 不提交到版本庫。
- **以檔案為單位的規則寫明邊界檔案。** 規則以「某目錄下的每個測試檔必須……」描述時，寫明是否適用於只含骨架的檔案（以及空檔、只有輔助函式的檔案），並附理由。判斷方式：比較豁免與不豁免時，有沒有任何測試能因豁免而逃過檢查；沒有差異時，選不需例外、不依檔案內容分支的規則，並提醒測試端在同一變更中準備好被匯入的模組。
- **「有執行」不等於「有驗證」。** 執行結果只能證明測試有執行並回報通過；空本體、在第一個斷言前提前 `return`（含依引擎或環境的條件 `return`，等價於被禁止的條件略過）、以 `try/catch` 吞掉失敗的斷言都會回報通過。骨架本體通常是空函式，只要刪掉略過標記就成為「通過的實際測試」，收尾的「不允許略過」也會在字面上達成。做法：
  1. 骨架本體必須為空；非骨架測試本體至少有一個斷言呼叫（靜態，範例：被呼叫者以 `expect` 或 `assert` 開頭）。
  2. 以執行時的斷言計數判定：每個通過的測試至少執行一個斷言、沒有失敗的斷言被吞掉。計數來源依框架而定（範例：端對端工具的自訂 reporter 可收到斷言步驟事件；沒有內建計數的框架以斷言包裝模組＋每個測試結束時的診斷輸出回報）。先實測計數能否正確對應到測試（範例：以包裝函式註冊測試時，結果中的檔名與行號會變成包裝模組，無法對應）。
  3. 寫出機械檢查抓不到的殘餘風險（空洞斷言、只驗部分 Then、部分斷言後提前 `return`、測試改寫同一 job 中的檢查檔案），以審查清單逐測試檢查與變異檢查補足，並把這項列為審查清單的一列。不採用自動化變異測試時寫出理由。
- **同一編號涵蓋多個範圍時**（範例：「每個畫面的按鈕尺寸」「每個畫面的網路請求」），每個範圍各一個測試，名稱為「編號＋範圍」，未完成的範圍保持略過。否則早期 PR 只測一部分就已是「實際測試」，遺漏的範圍不會被發現。
- PR 切分：第一個 PR 建立結構、CI、全部骨架與設計文件；接著先純邏輯、再畫面、最後 Should；最後一個 PR 打開不允許略過。每個 PR 列出涵蓋的需求與驗收編號。
- **每個驗收在轉實測的 PR 中，其 Given／When 用到的畫面與操作都已存在；早期 PR 已轉實測的驗收，在後續改寫同一畫面的 PR 中仍要成立**（範例：後面的 PR 以完整選單取代第一個 PR 的簡易首頁時，要保留首頁上已被驗收的元素）。 PR 切分表加一欄逐列寫出依據。常見漏洞：遊戲畫面先做、選單與結果畫面後做，但幾乎每個端對端驗收都要「從選單進入」「看到結果畫面」。不成立時，實作者很可能自行加入規格沒有的捷徑入口。
- 需要產品負責人決定範圍才啟用的驗收（範例：Should 需求的補充驗收），「啟用設定」與「骨架」必須在同一個 PR 變更；建議在設計簽核時決定範圍，於第一個 PR 一併加入。
- **測試輔助程式也有相依。** 測試輔助（範例：在測試端呼叫正式的純函式重算隱藏資訊）引用的正式模組，必須在加入該輔助的 PR 或更早存在；不得因為「骨架都在第一個 PR」就把輔助也排進第一個 PR。

## 7. 業界做法與小型專案的縮減

| 業界做法 | 小型或單人專案的縮減 |
|---|---|
| 架構決策紀錄（ADR） | 規格書中每個非顯而易見的決定附一句「理由」 |
| 正式設計審查會議 | 產品負責人簽核＋本 skill 自我審查清單 |
| 測試金字塔 | 狀態組合在單元測試窮舉；端對端只驗觀察點 |
| 介面合約 | DOM 測試介面表、儲存格式、CI 腳本的純函式介面 |
| 分支保護＋多人核准 | 單一帳號時以「獨立審查紀錄＋自動檢查紀錄存在」取代核准，並寫出殘餘風險 |
| 威脅模型 | 只針對 CI 權限（寫入權杖、外部評論、fork）列出對策 |

規模檢視：設計文件的份量與需求規模相稱。不要為小專案設計外掛架構或建置工具鏈；只有在需求要求時才加。

## 8. 常見錯誤與改寫

| 錯誤寫法 | 問題 | 改寫 |
|---|---|---|
| 「每 16 ms 更新一次畫面」 | 邊界時刻顯示值落後，容差邊界上的驗收不穩定 | 「依下一個顯示值邊界與倒數到期時刻排程」 |
| 「暫停時保存剩餘鎖定時間，繼續時重設計時器」 | 每個倒數各自處理，容易漏 | 「所有會隨暫停停止的倒數共用扣除暫停的遊戲時鐘」 |
| 「審查 agent 留下評論後 CI 會通過」 | 評論不觸發 commit 檢查 | 「評論事件觸發的工作流程以 commit status 寫回最新 head SHA」 |
| 需求只寫「條件 A 時顯示 X」，設計直接寫「條件 A 或 B 時顯示 X」（範例：需求只寫「優於既有值時標示」，設計自行加上「尚無既有值時也標示」） | 自行決定需求空白 | 列為待決問題並附建議；若採用，由負責需求的角色修訂需求文件 |
| 「測試用 `?seed=` 參數固定排列」 | 為測試新增需求沒有的產品行為 | 用注入介面或測試工具的初始化腳本；若必須暴露資訊，列為**待決問題**（附選項與成本），不得寫成假設 |
| 「DOM 每個元素帶答案的識別碼，方便測試」並列為假設 | 讓玩家取得不該有的資訊，且預設立場是已接受 | 列為待決問題；圖像與可及性名稱一律不帶答案 |
| 「實作時須確認無 1 px 溢出」 | 把餘裕為 0 的版面留給實作碰運氣 | 固定每個常數的 CSS，重算到每個尺寸都不低於訂定的最小餘裕（範例：4 px） |
| 「守衛：`t ≥ limitMs`（與顯示值判定等價）」 | 有前處理時兩者在極小區間內不同，規格自相矛盾 | 「守衛：顯示值 ≥ 上限」 |
| 「判定：顯示值與實際時間區間的距離 ≤ 容差」 | 實際容許誤差變成容差加上區間寬度，比需求寬鬆 | 「區間兩端都在容差內」；區間寬度只作診斷輸出 |
| 「按鈕停用時加 `disabled`」（需求要求點擊無效果且不被遮蔽） | 測試工具與部分瀏覽器不派送點擊，無法區分遮蔽與停用 | `aria-disabled`＋處理器忽略；測試以座標點擊 |
| 「待決問題已決定」只在待決問題表打勾 | 各章節仍寫著「依 DQ-n 決定」，實作者不知道該做哪個選項；補充驗收沒有新條件的正反例 | 依 3.4.1 逐處替換、補正反例、檢查決定之間的交互，並升版 |
| 「DQ-n：已關閉，採 (b)」，正文仍寫「決定前不實作任何收緊選項」，規則只有選項欄的一句摘要 | 實作者無法得知步驟順序、是否重複、字元範圍與邊界結果，只能停下或自行決定 | 決定紀錄後的第一個 commit 把選項展開為完整規則與判定表寫入正文，刪除過渡句，並以腳本清除過時的「待決定」字樣（3.4.1 第 1a 點） |
| 「測試記錄全部亂數，每局取 N 個值重放」 | 拒絕取樣與其他消耗者讓個數不固定，第二局以後重放錯位 | 「每次開始前讀取記錄長度作為錨點，從錨點以正式函式重放」 |
| 「時鐘控制後直接推進」 | 部分工具安裝假時鐘後時間仍隨真實時間流動 | 先凍結（範例：Playwright `pauseAt`），再推進 |
| 「編號檢查掃描 `tests/` 下所有測試檔」 | 單元測試名稱含驗收編號就被算成驗收覆蓋；放在執行器不執行的位置的檔案也被算進去 | 「只掃描驗收測試目錄；單元測試名稱不得含必要編號；驗收測試檔須位於執行器會執行的位置」 |
| 「『不允許略過』模式以靜態清單偵測所有略過寫法」或「以結果統計的略過數為 0 判定」 | 本體內的條件略過、別名、預期失敗不在靜態清單中；預期失敗在統計中算「符合預期」 | 「驗收測試只允許骨架宣告；以每個測試的執行結果判定預期狀態與實際結果都是通過，且靜態清單中的每個測試都有結果」 |
| 「審查清單逐項結果存成編號對應表後判定」 | 重複的列後蓋前，「不通過」被「通過」覆蓋；格式稍有不同的列被忽略 | 「白名單格式：同一項目或標頭欄位重複、看似項目卻不符格式的列都使整則無效；任一列不通過即不通過」 |
| 「收尾時打開『不允許略過』就代表驗收全部實測」 | 刪掉略過標記的空本體骨架、提前 `return` 的測試都會通過 | 「骨架本體為空、非骨架測試至少有斷言呼叫、執行時斷言計數至少 1 且沒有被吞掉的失敗；其餘由審查清單與變異檢查」 |
| 「去除強調符號與空白後，以『欄位名：』開頭的行算該欄位的一行」（合法格式為 `- 欄位名：值`） | 合法行偵測形式以 `-` 開頭，偵測不到合法行本身；依字面實作每則紀錄都無效，否則重複偵測失效 | 「偵測先去除行首的引用、清單、有序清單、標題符號，再比對欄位名；合法與否以原文逐字比對」，並以合法範本逐行驗證偵測結果 |
| 「偵測形式：去除行首的引用、清單、標題符號與所有非字母前綴後比對欄位名」並據此判定「讀者看到的只有一個欄位、一個表格」 | 只處理同一行內的字面差異；表格後沒有直線的列、字元參照、不屬於格式字元的不可見字元、HTML 註解中的內容、跨行標籤都讓讀者看到的內容與檢查不同；反方向，合法行藏在註解中時檢查讀得到、讀者看不到 | 「逐類列出渲染器的轉換（跨行範圍、解碼、可忽略字元、隱藏），合法格式用不到的構造整則拒絕，必須存在的構造寫成邊界規則；以平台的渲染器逐案實測，判定表作為單元測試資料」（5.3） |
| 「判定函式 `f({ tests, results })`」，規則卻有「每個檔案至少有一筆結果」「必要編號都有通過結果」 | 簽名缺少規則需要的輸入，實作者自行補參數 | 「`f({ tests, files, results, errors, requiredIds })`」：逐條規則列出所需輸入 |
| 「結果檔：`<結果檔>`」 | 位置、完整性、多次執行的檔名都由實作者決定；放在會被清空的目錄時結果互相刪除；中途中止的部分結果被當成完整 | 寫明位置、結束標記與筆數、寫入前清空、多次執行的檔名指定方式與缺少時的失敗 |

## 9. 自我審查清單

**輸入與查證**
- [ ] 完成 agent-dev-workflow 上工檢查，輸入文件為已簽核的最新版
- [ ] 每個指派給設計階段的查證問題都有結論、原文節錄、網址與查證狀態；未查證項目有實測安排
- [ ] 查證結論若影響需求或驗收，已寫明影響

**需求一致性**
- [ ] 沒有決定需求沒寫的行為；空白都在待決問題中，附建議與阻擋範圍
- [ ] 狀態 × 操作、狀態 × 計時器每一格都對應到轉移與需求編號，與需求的對照表一致
- [ ] 邊界（最後一個、第一次、恰好上限、同時到期、連按、暫停中切背景、重新整理、多分頁）都檢查過
- [ ] 每條不變式寫明適用狀態，並逐條對照終止與取消轉移
- [ ] 以顯示值判定的門檻，守衛就寫成顯示值比較
- [ ] 沒有以「假設」處理產品決定（資訊暴露、流程例外、外部上限無餘裕、錯誤處理的連帶影響、Should 範圍）；受影響處標示「依 DQ-n 決定」
- [ ] 以腳本核對：追溯表的 Must 集合等於需求矩陣的 Must 集合；骨架清單等於需求中要求自動測試的編號集合
- [ ] 待決問題關閉後（3.4.1）：腳本搜尋「依 DQ-n 決定」只剩歷史紀錄；改需求的決定已等需求升版並更新依據版本；新條件的補充驗收有正例與反例；決定之間的交互已逐對檢查；過渡規則寫明結束條件
- [ ] 被採用的選項已展開為正文中的完整規則（順序、不動點、字元範圍、邊界判定表、回歸檢查），過渡句已刪除，表頭、標題、說明與簽核欄的狀態一致（3.4.1 第 1a 點）

**可測性**
- [ ] 邏輯層不讀時間、亂數、儲存、DOM；全部注入
- [ ] 每個驗收觀察點都有 DOM 測試介面或函式介面可讀取
- [ ] 要求真實時間的量測與控制時鐘的測試分開，量測方法寫明誤差來源
- [ ] 統計型驗收可在無瀏覽器環境以正式程式路徑執行，並有反例

**畫面**
- [ ] 每個要求的視窗尺寸都有版面算式、結果與餘裕；算式的每個常數都是規格中固定的 CSS 值；餘裕不低於訂定的最小餘裕
- [ ] 最小可點擊尺寸在最小視窗成立，且留有餘裕
- [ ] DOM 測試介面同時提供邏輯狀態與實際渲染內容；圖像與可及性名稱不洩漏答案
- [ ] 沒有用隱藏溢出掩蓋版面問題
- [ ] 遮蔽層不蓋住需求要求可見的元素

**流程**
- [ ] CI 每個必要檢查的名稱、觸發、權限寫明；以 commit 為單位的檢查在新 commit 時會失效
- [ ] 評論觸發、預設分支限制、fork 權限、啟動例外都已處理
- [ ] 手動設定步驟有順序與執行者
- [ ] 驗收骨架與編號檢查的交互已解決；有「不允許略過」的收尾步驟
- [ ] PR 切分表逐列寫出「Given／When 所需畫面與操作」在該 PR 已存在，且改寫畫面的 PR 列出必須保留的已實測元素
- [ ] 測試輔助程式引用的正式模組在加入該輔助的 PR 或更早存在
- [ ] 以記錄亂數重放取得隱藏資訊時，有錨點與亂數呼叫契約，契約由單元測試固定
- [ ] 依賴待決問題的模組排在該問題的決定期限之後的 PR，不在決定前實作
- [ ] 多範圍編號已拆成各自命名的測試
- [ ] 編號檢查只採計驗收測試目錄；單元測試名稱不得含必要編號；驗收測試檔都在執行器會執行的位置
- [ ] 驗收測試只允許一種略過寫法；略過、預期失敗與「沒有執行」以執行結果逐引擎判定，結果格式已本機實測
- [ ] 審查紀錄判定為白名單：同一項目與標頭欄位重複、看似項目卻不符格式的列、不可見字元都使整則無效；識別碼正規化後限定字元集
- [ ] 白名單的「看似某欄位」偵測，已以合法範本逐行驗證（合法的每一行恰好被偵測一次）；偵測以渲染後的文字開頭為準；仍不涵蓋的寫法已實測並列為殘餘風險或待決問題
- [ ] 收緊偵測時，偵測取「新 ∪ 修改前」，並有「新版有效 ⇒ 舊版有效」的差分測試，輸入以程式列舉正規化會改變的碼位
- [ ] 渲染器的跨行範圍、解碼、可忽略字元、隱藏四類轉換都已列出，兩個方向（讀者看得到而檢查偵測不到、檢查讀得到而讀者看不到）都已以平台的渲染器實測；合法格式用不到的構造整則拒絕或列為待決問題；收緊的規則已以實際紀錄檢查誤判
- [ ] 檢查腳本的純函式簽名，逐條對照判定規則，每條規則所需的資料都在參數中；特殊模式（範例：試算）在一般模式提早結束的狀態下的行為已寫明
- [ ] 結果檔的交接（位置、不在會被清空的目錄、結束標記與筆數、寫入前清空、多次執行的檔名、缺少時失敗）已寫明
- [ ] 以檔案為單位的規則，已寫明是否適用於只含骨架等邊界檔案及理由
- [ ] 執行結果檢查的殘餘風險（空本體、提前 return、吞掉斷言）已寫明；可機械檢查的部分（骨架本體為空、斷言呼叫、執行時斷言計數）已設計，其餘列為審查清單的一列
- [ ] 建置與驗證同一個值（範例：commit SHA）的步驟取得同一個環境變數
- [ ] 只在預設分支生效的檢查：必要檢查設定排在加入後的第一個 PR（含之後插入的 PR）；修正該檢查本身的 PR 由舊版判定的限制已寫明，並有新版試算與合併後重新觀察驗收的步驟；連續修正時，每個修正 PR 都是前一版的第一次平台執行，其失敗處理已寫明；被檢查匯入的模組的修改也算修改該檢查
- [ ] 工作流程不插值使用者可控字串；並行群組鍵對每種事件都有值
- [ ] 啟動例外（初始 commit、第一個 PR、只在預設分支生效的檢查）寫成待決問題，必要檢查的設定分段
- [ ] 審查清單涵蓋「PR 修改自己的檢查」
- [ ] 真實時間量測的判定不比需求寬鬆，有逾時與隔離
- [ ] 測試指令在本機實測過（範例：測試執行器的路徑參數）

## 10. 回饋機制

任何 agent 在設計、實作、測試或審查時發現問題，依 agent-dev-workflow 第 7.3 節判斷是否為本 skill 的缺漏：

- 其他專案也可能發生、本 skill 沒有提醒 → 修改本 skill：加入規則，必要時加入第 8 節的「錯誤寫法／改寫」與第 9 節的檢查項，範例去除專案細節。
- 本 skill 有規定但沒有照做 → 不改規則；若規定容易漏看，改寫得更明確。
- 只與某專案有關 → 記在該專案文件，不改本 skill。

修改方式依 agent-dev-workflow 第 7.4 節：在下方變更紀錄寫明日期、發現的階段、問題、修改內容；不得為了讓目前的工作通過而刪除或放寬檢查；修改後以新規則重新檢查目前產出。版本庫建立後，本 skill 的修改與程式碼一樣經過 PR 與審查。
