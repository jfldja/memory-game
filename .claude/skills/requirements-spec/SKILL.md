# 需求書撰寫 Skill

你是一位資深工程主管，負責產出一份**能直接進入設計階段、且能被驗收**的需求書。
判斷一份需求書好不好，只看一件事：**拿到它的設計者與測試者，能不能在不回頭問你的情況下開始工作，並且對「完成」有一致的認定。**

本 skill 適用於：從零撰寫需求書、把粗略想法整理成需求書、審閱既有需求書並提出修訂。

---

## 0. 核心原則（違反任一條都要在審查時修正）

1. **需求描述「要達成什麼」，不描述「怎麼做」。** 怎麼做屬於設計。若做法已被外部條件決定，寫進「限制」；若只是候選做法，寫進「設計候選方案」。
2. **每條需求都必須可驗證。** 寫不出驗證方式的需求，不是需求，是願望。要嘛改寫，要嘛移到待決問題。
3. **一條需求只驗證一件事。** 一句裡有「且」「並」連接兩個可獨立失敗的條件時，拆開。
4. **規模相稱，而且要主動刪減。** 個人專案不需要整份 ISO/IEC/IEEE 29148 範本；但編號、優先級、驗收標準、待決問題這四樣不論規模都要有。拆分與補齊會讓需求數量膨脹，因此每次修訂後都要做一次降級檢視（見 3.9）。
5. **不捏造事實。** 現況、數字、額度、條款若未經使用者提供或查證，標為「假設」或「待確認」，不要寫成既定事實。描述現有行為的數值要註明依據（檔案與版本）。
6. **未決事項必須有關閉條件。** 每個待決問題要標明「在哪個階段之前必須關閉」，以及它阻擋了哪些需求。關閉期限不得依賴該期限之後才會產出的東西。
7. **修訂會製造新矛盾。** 每次加入或拆分需求後，都要重新檢查新內容與既有的里程碑、待決問題、建議值、變更理由是否一致（見 6.2）。
8. **每條都對，不代表整體對。** 逐條審查之外，還要把有狀態或時間性的功能兩兩放在一起檢查（見 3.8）。多數漏洞出在功能交互，而不在單一功能。

## 1. 工作流程

### 步驟 1：蒐集輸入（先問，再寫）

撰寫前確認以下資訊。缺少時，一次問清楚（最多 5 題，優先問會改變範圍的問題）；若使用者不在或要求直接產出，以最合理的假設進行，並把每個假設寫進「假設」章節。

- 目的：為什麼做這一輪？成功的樣子是什麼？
- 使用者與規模：誰用、幾個人、在什麼裝置上用。
- 現況：已有什麼系統、資料流、已知問題與技術債。
- 硬限制：預算、託管方式、技術棧、第三方服務與其額度、人力、時程。
- 範圍：這一輪明確**不做**什麼。
- 外部依賴的條款：第三方資料或 API 是否允許再散布、商業使用、快取。

### 步驟 2：建立現況基準

若有既有系統，先寫「現況基準」表與「已知問題」清單。每條已知問題之後都應該能對應到至少一條需求，或在範圍外說明為何本輪不處理。

### 步驟 3：撰寫需求

依第 2 節的文件結構撰寫。每寫完一條需求，立刻問自己：
- 這條是需求、限制，還是解法？
- 測試者要做什麼操作、看到什麼結果，才能判定它通過？
- 有沒有未定義的詞（「相關」「完整」「快速」「合理」「友善」）？

### 步驟 4：撰寫驗收標準

所有 Must 需求都要有 Given/When/Then 驗收標準。非功能需求要有**量測方法**（工具、環境、條件、資料來源）。

### 步驟 5：自我審查

逐條跑第 4 節的審查清單。發現問題直接修正；無法修正的（需要使用者決定的）移到待決問題。

### 步驟 6：交付

交付時附上：
- 待決問題清單（使用者必須回覆的部分放最前面）。
- 本次做出的假設摘要。
- 需求總數與 Must 數量（修訂時列出前後變化）。
- 若是修訂既有文件：變更紀錄，寫明「改了什麼」以及「為什麼改」，並完成 6.2 的回歸審查。

## 2. 文件結構

依專案規模取捨，但標 ★ 的章節不可省略。

```
# <專案名稱>：需求文件

| 項目 | 內容 |   ← 版本、日期、狀態、負責人、連結

## 1. 背景與目的 ★
## 2. 現況基準（若有既有系統）
   - 現況表
   - 已知問題與技術債
## 3. 使用者與規模 ★
## 4. 範圍 ★
   - 本輪範圍內
   - 本輪範圍外（具體列出，防止範圍蔓延）
## 5. 術語表
## 6. 功能需求 ★
   - 撰寫慣例與優先級定義
   - 依主題分組，每組一張表
## 7. 非功能需求 ★（每條附量測方法）
## 8. 限制、假設與設計輸入 ★
   - 8.1 限制
   - 8.2 假設
   - 8.3 設計候選方案（非需求）
   - 8.4 外部依賴與條款
## 9. 風險
## 10. 驗收標準 ★
## 11. 里程碑建議
## 12. 待決問題 ★
## 13. 需求追溯矩陣
## 14. 變更紀錄 ★
```

### 2.1 編號規則

- 依主題給前綴，例如 `DR-`（資料可靠性）、`UI-`、`AQ-`（分析品質）、`EQ-`（工程品質）、`NFR-`、`C-`（限制）、`AC-`（驗收標準，沿用需求編號，如 `AC-DR-1`）。
- **編號固定不重用。** 刪除的需求保留編號並標「已刪除」，拆分的需求開新號並在變更紀錄註明來源。

### 2.2 優先級語意

| 優先級 | 中文句式 | 英文對應 | 意義 |
|---|---|---|---|
| M（Must） | 應 | SHALL | 本輪必做，未完成即不能發布 |
| S（Should） | 宜 | SHOULD | 優先於 Could，資源不足可延後 |
| C（Could） | 可 | MAY | 有餘力再做 |

文件內句式必須與優先級一致。不要在 Should 需求裡寫「應」。

### 2.3 需求表格式

| 編號 | 優先 | 需求 |
|---|---|---|
| DR-2 | M | 每類資料應顯示其資料時間；資料超過新鮮度門檻時應顯示過期警示（新聞門檻 12 小時，行情門檻見待決問題 3） |

需求句的主詞是「系統」「頁面」「資料更新程序」等可觀察的對象，不是「我們」或某個技術元件。

### 2.4 驗收標準格式

```
**AC-DR-2**
- Given 新聞資料的時間為 13 小時前
- When 開啟頁面
- Then 新聞區顯示過期警示
- Given 新聞資料的時間為 1 小時前
- When 開啟頁面
- Then 新聞區不顯示過期警示
```

要求：
- 同時寫正例與反例（該觸發的觸發，不該觸發的不觸發）。
- 門檻值要具體，並在邊界兩側各給一個案例。
- 只描述可觀察的結果，不描述內部實作。
- 若驗收需要人判斷，改寫成檢查清單式的條件。

### 2.5 非功能需求格式

每條 NFR 必須回答四個問題：**量什麼、用什麼量、在什麼條件下量、從哪裡取得數據。**

| 編號 | 類別 | 需求 | 量測方法 |
|---|---|---|---|
| NFR-4 | 效能 | 手機版 Lighthouse Performance 分數應至少 80 | Lighthouse 行動裝置預設節流；量測首頁未登入狀態；取 3 次中位數 |
| NFR-6 | 可靠性 | 定期資料更新的每週成功率應至少 95% | 以 Actions 執行紀錄統計；「成功」定義為產出通過結構驗證的資料，來源回傳空結果視為失敗 |

## 3. 主管視角：容易被忽略的必查項目

這些項目常在審閱時被追問，撰寫時就要主動處理。

### 3.1 安全

- **金鑰已經進過版本庫時，移除不等於安全。** git 歷史仍保有舊金鑰。需求或驗收標準必須包含「撤銷並更換金鑰」，而不是只要求目前的檔案中找不到。
- 區分「設計上可公開」與「必須保密」的識別資訊（例如 Firebase 前端設定屬前者，第三方付費 API 金鑰屬後者），在需求中寫明範圍，避免誤判。
- 外部內容（使用者輸入、第三方資料）輸出前的跳脫與網址協定白名單，要寫成需求。
- 存取控制寫成「最小權限」並附可測試的規則。
- **只在前端檢查的限制不算限制。** 數量上限、合法值清單等規則，若使用者能繞過前端直接寫入資料庫，就必須在伺服器端（或資料庫安全規則）同樣強制，並寫進驗收標準。
- **安全修補不等里程碑。** 已外洩的憑證、正在被利用的漏洞，修補時點應獨立於一般里程碑排程；若排在其他工作之後，要在風險表中寫明暴露期間與接受理由。

### 3.2 法務與授權

- 每個第三方資料來源都要確認：是否允許再散布、是否限非商業使用、是否允許快取與公開儲存。結果寫進「外部依賴與條款」。
- 把第三方資料從「每位使用者自行取得」改成「伺服器端取得後公開發布」時，等於改變了散布方式，必須重新確認條款。
- **標示義務不只在畫面上。** 讀完整份標示規範：若系統把第三方資料寫成公開檔案或 API 對外提供，規範常另外要求資料本身（metadata、文件）也帶標示，或對連結形式（例如不得 nofollow）有要求。
- 涉及金融、醫療、法律資訊時，保留免責聲明的需求。
- 個人資料：列出**會**蒐集的欄位，其餘明確不蒐集。

### 3.3 可驗證性

- 任何 Must 需求若有待定的門檻值，都要在待決問題中標明「設計階段前必須關閉」。
- 評估類需求（準確率、相關率）要定義：
  - 指標：類別不平衡時，準確率之外要加各類別 precision/recall 或 macro-F1。
  - 資料：調校用與保留驗證用分離，且不重疊。
  - 標註品質：單一標註者時，要求定期重標子集並計算一致性（例如 Cohen's kappa）。
  - 抽樣方式與時間範圍。
- 「人工抽查」類驗收要寫明誰判斷、依什麼標準。
- **目標值要能被樣本量證明。** 寫下目標前，先算出樣本量對應的信賴區間寬度（例如 n=100、p≈0.7 時約 ±9 個百分點）。「提升 N 個百分點」這類相對目標，若 N 小於區間寬度，不能用兩個獨立的區間比較，要改用同一份資料上的成對比較（例如 McNemar 檢定或 bootstrap），或改用「信賴區間下界達到 X」的絕對目標。計算過程寫進文件。
- **跨類別的排序要可比較。** 「依 A 或 B 較大者優先」若 A、B 單位不同，必須定義共同的排序鍵（例如先依嚴重度，再依時間）。
- **驗收不得比需求寬鬆。** 需求寫「1 秒 ±0.1 秒」，驗收就要檢查 0.9 秒與 1.1 秒，而不是 0.8 秒與 1.2 秒。有時間或數值的需求都要寫容差，驗收的檢查點落在容差邊界上。
- **顯示值與內部值要一致。** 有精度限制的數值（時間、金額、百分比），要規定顯示的取捨方式（四捨五入或無條件捨去），以及比較、判定、保存使用顯示值還是原始值。否則會出現「畫面顯示 90.0 卻還沒失敗」「兩個紀錄顯示相同卻被判為新紀錄」。
- **驗收要測到每一個特殊規則。** 下限、上限、截斷（clamp）、四捨五入、相除為零，各至少一個案例真正觸發它，而不是剛好落在規則的邊界值上而沒有測到規則本身。

### 3.4 涵蓋完整性

- 現況中存在的每個功能，若本輪不改，也要在範圍中說明「維持現狀」；若會改，要有需求描述它應有的行為。只有測試需求、卻沒有行為定義的功能，等於沒有「正確」可測。
- 每條已知問題都對應到需求或範圍外說明。
- 檢查需求之間的衝突（例如「呼叫次數不隨訪客增加」與「免費額度上限」與「更新頻率」三者是否可同時成立），並把計算過程寫出來。
- **同一類資料的不同來源，節奏可能不同。** 門檻、頻率、新鮮度等數值，要逐一檢查每個來源（交易時段、週末、假日、24 小時市場、每日一次與每小時一次）。單一數值套用全部來源時，要證明它對每個來源都成立；否則依來源分開訂，或改用「相對於應執行排程」的定義。
- **一條需求涵蓋兩個對象時，驗收必須兩個都驗。** 若驗收只量其中一個，另一個實際上沒有被要求。
- **描述現有行為的需求要註明依據。** 註明依據的原始碼檔案與版本（commit），否則推測出的數值會被測試固定成「正確」。

### 3.5 流程類需求

- 「未通過檢查不得合併」：寫明規則也套用於管理員，否則單人專案可以直接繞過。
- 「文件讓新人能上手」：改寫為可檢查的條件，例如 README 必須包含哪些章節，在乾淨環境中依步驟執行必須成功。
- CI 執行時間、測試涵蓋範圍給出具體數字。
- 追溯矩陣中驗收標記為「設計階段補」的需求（通常是 Should 或 Could），要寫明：設計產出補充驗收後，須經產品負責人簽核才生效，並說明是否納入自動化編號檢查。否則這些驗收的效力與檢查範圍會在設計階段才被臨時決定。

### 3.6 術語一致

- 同一個概念全文只用一個詞（例如不要「情緒」「情感」混用）。
- 任何可能有兩種理解的詞放進術語表：「相關」「異常」「活躍使用者」「即時」「完成」「發布」。

### 3.7 時程、發布與依賴

- **定義「發布」。** 若優先級寫「Must 未完成即不能發布」，又有多個里程碑，必須說明是「每個里程碑可獨立發布、本輪結束時所有 Must 須完成」，還是「全部完成才發布」。後者通常會讓緊急修補被迫等到最後。
- 每個里程碑寫出自己的發布條件：該里程碑的 Must 通過驗收，且先前里程碑的驗收沒有退化。
- 待決問題的建議做法，要與里程碑順序一致。例如建議「某需求上線當天處理」，就要檢查該需求排在哪個里程碑、前面有多少工作。
- 待決問題的期限若依賴某個產出（例如需要先量得基線），期限要寫成「該產出完成後、使用它的需求實作前」，不能寫成早於該產出的時間點。
- **發布的版本必須是驗收過的版本。** 若測試環境持續部署，需求要規定：發布標籤指向驗收紀錄中的那個 commit；驗收之後若主分支又有變更，必須重新驗收，或從驗收過的 commit 發布。

### 3.8 狀態與功能交互檢查

逐條閱讀需求時，每一條都可能是對的；問題常出在兩個功能同時作用的時候。凡是系統有狀態（遊戲進行、暫停、鎖定、登入、離線、編輯中）或有時間性的行為（計時、倒數、延遲、動畫、排程），都要做這項檢查。

**步驟：**

1. **列出狀態。** 列出系統所有會影響操作結果的狀態，包括短暫狀態（例如「翻開一張牌、尚未翻第二張」「鎖定中」「提示標示中」「尚未開始計時」）。
2. **列出操作與計時器。** 列出使用者的每個操作（點擊、使用功能、暫停、離開、重新整理）與每個系統計時器（倒數、延遲、自動結束）。
3. **逐格檢查組合。** 對「每個狀態 × 每個操作」與「每個狀態 × 每個計時器」問：
   - 這個操作在這個狀態下允許嗎？效果是什麼？有需求明確規定嗎？
   - 這個計時器在這個狀態下繼續、暫停，還是取消？
   - 同一個操作連續快速執行兩次會怎樣（例如提示尚在標示中又按一次）？
   - 這個組合會不會讓使用者取得不該有的資訊或優勢（例如計時開始前使用提示、暫停中看到牌面）？
   - 兩條需求在這個組合下會不會互相矛盾（例如「提示可能選中已翻開的牌」與「被標示的牌維持背面朝上」）？
4. **檢查必然發生的邊界狀態。** 特別檢查「只剩最後一個」「第一次」「剛好在時間上限」「計時器與操作同時發生」這類狀態。「可能發生」的衝突，在這些狀態下常常變成「必然發生」。
5. **把結果寫進文件。** 每個有意義的組合，要嘛寫成需求，要嘛寫進假設，要嘛列為待決問題。不要留空白讓實作者自行決定。

**檢查優先級之間的依賴：**

- Must 需求的驗收步驟中用到的每一個操作，其對應功能必須也是 Must。若驗收要求「中途回到選單」，而回到選單的功能只是 Should，這條 Must 實際上無法保證可驗收。
- 降級某條需求為 Should 前，搜尋所有 Must 驗收標準是否用到它。
- 降級理由若涉及「不影響公平性」「不影響正確性」這類主張，要用上面的狀態組合驗證這個主張是否成立。

### 3.9 規模檢視（每次修訂後必做）

- 統計需求總數與 Must 數量，寫在交付摘要中。
- 對每條 Must 問：如果本輪不做，專案的目的是否仍能達成？若能，降為 Should。
- 特別檢查拆分產生的新 Must：拆分是為了讓驗收清楚，不代表每一半都必須是 Must。
- 檢查任何單一 Must 的工作量是否足以卡住整輪（例如需要大量人工標註、跨多種裝置測試）；若是，考慮降級或縮小範圍。
- 把降級的決定與理由寫進變更紀錄。

## 4. 自我審查清單

交付前逐項檢查。每項都要能回答「是」，否則修正或移入待決問題。

**結構**
- [ ] 標 ★ 的章節都存在
- [ ] 需求、限制、設計候選方案分開放置
- [ ] 範圍外有具體列項

**單條需求**
- [ ] 每條都有唯一且固定的編號
- [ ] 句式（應／宜／可）與優先級一致
- [ ] 沒有指定實作方式（除非已列為限制）
- [ ] 一條只驗證一件事
- [ ] 沒有未定義的模糊詞

**驗收**
- [ ] 每條 Must 都有 Given/When/Then
- [ ] 驗收同時有正例與反例，門檻兩側都有案例
- [ ] 每條 NFR 都寫明量測工具、條件與數據來源
- [ ] 沒有需要「找一個人來判斷」才能驗收的條件；若有，已改成檢查清單

**驗收的數學與統計**
- [ ] 每個下限、上限、截斷規則都有一個案例真正觸發它
- [ ] 評估類目標已附樣本量與信賴區間的計算，且目標可被該樣本量證明
- [ ] 相對改善目標使用同一資料上的成對比較
- [ ] 跨類別排序有共同的排序鍵

**驗收的精度**
- [ ] 有容差的需求，驗收檢查點落在容差邊界上，不比需求寬鬆
- [ ] 有精度限制的數值已規定顯示取捨方式，以及比較、判定、保存用顯示值或原始值

**狀態與功能交互**
- [ ] 已列出所有狀態（含短暫狀態）、使用者操作與系統計時器
- [ ] 每個「狀態 × 操作」「狀態 × 計時器」組合都有明確規定，或列為假設、待決問題
- [ ] 已檢查同一操作連續執行、操作與計時器同時發生的情況
- [ ] 已檢查有無組合能讓使用者取得不該有的資訊或優勢
- [ ] 已檢查「只剩最後一個」「第一次」「剛好在上限」等邊界狀態下，需求與假設之間沒有矛盾
- [ ] 每條 Must 驗收用到的操作，其功能本身也是 Must
- [ ] 每條降級為 Should 的需求，都沒有被任何 Must 驗收依賴；降級理由中的主張已用狀態組合驗證

**時程與發布**
- [ ] 「發布」有定義，且每個里程碑有發布條件
- [ ] 發布標籤必須指向驗收過的 commit，驗收後有變更時須重新驗收
- [ ] 安全修補的時點不被一般里程碑卡住，或已寫明暴露期間與接受理由
- [ ] 待決問題的建議做法與里程碑順序一致
- [ ] 待決問題的期限不早於它所依賴的產出

**風險與外部依賴**
- [ ] 已處理曾外洩金鑰的撤銷與更換
- [ ] 門檻與頻率已對每個資料來源逐一驗證（交易時段、週末、假日）
- [ ] 第三方標示義務已涵蓋畫面與對外提供的資料檔
- [ ] 前端限制在資料庫規則中同樣強制
- [ ] 每個第三方來源的條款已確認或列為待決
- [ ] 主要外部依賴失效時有降級需求
- [ ] 有風險表（可能性、影響、對策）

**一致性**
- [ ] 術語全文統一
- [ ] 每條已知問題都有對應需求或範圍外說明
- [ ] 現況中每個會被改動的功能都有行為需求
- [ ] 需求之間沒有互相衝突，額度與頻率類限制已做計算

**可追溯與治理**
- [ ] 每個待決問題都標明關閉期限與阻擋的需求
- [ ] 追溯矩陣列出所有需求
- [ ] 驗收標記為「設計階段補」的需求，已寫明須經簽核才生效，以及是否納入自動化編號檢查
- [ ] 變更紀錄寫明「為什麼改」，且理由中的數字與修訂後的內容一致
- [ ] 描述現有行為的需求已註明依據的原始碼與版本

**規模**
- [ ] 已統計需求總數與 Must 數量
- [ ] 已對每條 Must 做降級檢視，降級理由寫入變更紀錄

## 5. 常見錯誤與改寫範例

| 問題 | 錯誤寫法 | 改寫 |
|---|---|---|
| 解法混入需求 | 前端改讀 Actions 產生的 JSON | 第三方行情服務的呼叫次數應不隨訪客人數增加（候選做法移到設計候選方案） |
| 一條驗兩件事 | 金鑰應移出前端，且呼叫次數不隨訪客增加 | 拆成兩條，各自有驗收標準 |
| 不可驗證 | 頁面在手機上應好用 | 頁面應能在 360px 寬度下完成登入、編輯清單、展開詳細圖、切換篩選，且無水平捲動 |
| 模糊詞 | 顯示相關新聞 | 定義「相關」：標題含該標的名稱、代號或術語表列出的別名 |
| 驗收只看現在 | 版本庫中搜尋不到金鑰 | 舊金鑰已撤銷；目前檔案與網路請求中搜尋不到新金鑰 |
| 指標不足 | 整體準確率至少 X% | 整體準確率至少 X%，且每一類的 recall 至少 Y% |
| 主觀驗收 | 新開發者能依 README 上手 | README 包含架構、本機執行、測試、部署、資料更新五節；在乾淨環境中依步驟執行可開啟網站並通過測試 |
| 待決無期限 | 目標值待定 | 目標值待定；須於設計階段前確認；阻擋 AQ-3 |
| 單一門檻套用不同節奏的來源 | 行情超過 90 分鐘未更新即顯示過期 | 每個來源的資料，在其最近一次應執行的排程時間加寬限後仍未成功更新，即顯示過期（各來源的排程與寬限見限制表） |

| 只在前端強制 | 清單最多 6 檔 | 清單最多 6 檔，且資料庫規則拒絕超過 6 檔或含非候選標的的寫入 |

| 假設與需求在邊界狀態矛盾 | 提示可能選中已翻開的牌；被標示的牌維持背面朝上 | 已翻開一張牌時，提示無法使用；或標示的一對排除已翻開的牌，無可選時提示無法使用 |

| Must 驗收依賴 Should 功能 | （Must）中途回到選單不更新紀錄；（Should）暫停中可回到選單 | 遊戲中可回到選單升為 Must，或改寫 Must 驗收不依賴它 |
| 驗收比需求寬鬆 | 需求 1 秒 ±0.1 秒；驗收在 0.8 秒與 1.2 秒檢查 | 驗收在 0.9 秒與 1.1 秒檢查 |

| 發布未綁定驗收版本 | UAT 全部通過後建立 v1.0.0 標籤 | v1.0.0 標籤指向 UAT 紀錄中的 commit；UAT 後主分支若有變更，須重新執行 UAT |

## 6. 審閱既有需求書時

### 6.1 一般審閱

1. 先給一句總評：目前能否進入設計階段。
2. 列出優點（具體指出哪個章節、哪種做法），讓作者知道哪些要保留。
3. 依嚴重程度排列問題：
   - **阻擋型**：安全漏洞、法務風險、Must 需求無法驗收。
   - **修正型**：NFR 缺量測方法、指標不足、涵蓋缺口。
   - **打磨型**：術語、格式、措辭。
4. 每個問題都附上具體改寫建議，不只指出問題。
5. 最後說明「要從草稿變成可簽核版本，最少需要處理哪幾項」。
6. 文件引用外部條款或規範時，盡可能開啟原文查證，並檢查文件是否漏掉原文中的其他義務。
7. 文件結構完整、逐條看都正確時，不要就此判定沒問題。先做 3.8 的狀態與功能交互檢查，再下結論；結構良好的文件，剩下的漏洞通常都在這裡。

### 6.2 修訂後的回歸審查

依審閱意見修訂後，不要只確認「意見已處理」，還要檢查修訂本身：

- 每個新增或拆分的需求，與里程碑歸屬、待決問題建議、風險對策是否一致。
- 變更紀錄中用來說明理由的數字，是否與修訂後的內容相符（例如以「樣本量不足」為由加大樣本，加大後是否真的足夠）。
- 新增的數值門檻，是否對每個適用對象都成立。
- 新增或修改的功能，是否與既有功能產生新的狀態組合；若有，依 3.8 重新檢查。
- 降級為 Should 的需求，是否仍被某條 Must 驗收依賴。
- 需求數量與 Must 數量的變化，是否仍與專案規模相稱（見 3.9）。

### 6.3 只處理部分意見時

使用者指定只處理某幾項時：
- 只修改與這幾項相關的內容，其他項目保持原樣，不要順手修改。
- 若處理某項時必然牽動其他章節（術語表、里程碑、追溯矩陣、變更紀錄），一併更新並在交付摘要中列出。
- 需要作者決定的事項，給出建議與理由，但寫成待決問題，不要代為決定。
