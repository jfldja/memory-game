# 實作階段 Skill

本 skill 規範「如何把已簽核的設計變成可審查、可驗收的程式碼」。它與專案無關；文中出現的檔名、數值、指令都標示為「範例」。

搭配使用：開發流程與角色依 `agent-dev-workflow`；設計產出的格式依專案的設計 skill（若有）。

---

## 0. 核心原則

1. **設計是唯一依據。** 實作只做規格書寫了的事。規格沒寫、寫得互相矛盾，或外部事件讓某條規則已經過時，停下來回報，不自行補上。
2. **寫程式的人不判定自己合格。** 不撰寫、不修改驗收測試與其骨架；模組單元測試不得使用驗收編號命名（第 4.3 節）。
3. **檢查只能變嚴，不能變寬。** 為了讓 CI 通過而縮小掃描範圍、增加例外、降低門檻，一律禁止。發現檢查本身有漏洞，回報設計階段，並在交付摘要寫明。
4. **判定邏輯寫成純函式。** 腳本的「判定」與「讀檔、呼叫 API、結束程式」分開，判定可以直接單元測試，外層只是薄包裝。
5. **能在本機驗證的都驗證；不能的寫清楚。** 交付摘要分開列出「本機已驗證」與「只能在平台上驗證」的項目。

---

## 1. 輸入與產出

**輸入（缺任何一項就停下來回報）：**

- 已簽核的需求文件與設計文件（規格書、模組測試標準、驗收骨架計畫、審查流程）。
- 本次 PR 在設計「PR 切分」中的範圍，以及哪些部分屬於測試 agent。
- 工作階段識別（寫入 PR 說明的作者段落）。

**產出（交付統籌 agent）：**

| 產出 | 內容 |
|---|---|
| 程式碼 | 只含本 PR 範圍；每個 commit 能對應到設計或需求編號 |
| 模組單元測試 | 涵蓋模組測試標準列出的行為與邊界；名稱不含驗收編號 |
| 本機驗證紀錄 | 執行過的指令與結果；無法本機驗證的項目與原因 |
| 給測試 agent 的介面說明 | 測試需要呼叫的函式簽名、檔案位置、命名規則、限制 |
| PR 說明草稿 | 依專案 PR 範本 |
| 設計問題清單 | 空白、矛盾、已過時的規則；附發現情境與建議 |
| skill 修改 | 本 skill 的修改與變更紀錄 |

---

## 2. 步驟

1. **上工檢查。** 依 agent-dev-workflow 第 1 節。讀完需求、規格書中本 PR 相關章節、模組測試標準、審查清單。
2. **列出本 PR 的範圍與分工。** 從設計的 PR 切分表抄出：本 PR 的檔案、需求編號、要轉實測的驗收；哪些檔案屬於測試 agent。不確定歸屬時先問。
3. **核對設計與現況。** 設計寫於過去，版本庫可能已經變了（範例：設計寫「同步 PR 合併前採過渡規則」，而同步已先完成）。逐項確認設計的前提仍成立；不成立時依設計中「事件之後」的路徑做，並回報。
4. **先寫判定的純函式與單元測試，再寫外層。**
5. **本機驗證**（第 5 節）。
6. **以多個有意義的 commit 提交。** 一個 commit 一個主題（範例：設定檔、建置、某支檢查腳本、工作流程），訊息寫明對應的設計章節。
7. **自我審查**（第 8 節），撰寫交付摘要。

## 3. CI 工作流程與檢查腳本

### 3.1 工作流程的安全

| 陷阱 | 後果 | 做法 |
|---|---|---|
| 在 `run:` 以 `${{ }}` 插值評論、PR 標題或說明、分支名稱 | 指令注入 | 只以 `env:` 傳入數字或 SHA；其餘由腳本經 API 或事件檔讀取。以靜態測試固定「`run:` 內沒有 `${{`」 |
| 具寫入權杖的事件（範例：GitHub `pull_request_target`）未指定簽出的分支 | 預設簽出的是 PR 的**目標分支**，不一定是預設分支 | 明確指定預設分支（範例：`ref: ${{ github.event.repository.default_branch }}`）；不簽出 PR 的程式碼 |
| 簽出後保留權杖 | 後續步驟（含被汙染的相依）可取得權杖 | `persist-credentials: false` |
| 第三方 action 只寫主版本標籤 | 標籤可被移動 | 以完整 commit SHA 固定，旁註版本；固定前讀該 SHA 的 `action.yml`，確認輸入名稱（新主版本常改名或新增預設開啟的快取） |
| 寫入權杖的工作流程安裝套件或使用快取 | 快取或相依被汙染 | 不安裝、不快取；腳本只用執行環境內建模組 |
| 腳本把使用者可控字串印在行首 | 平台把它當成工作流程指令（範例：GitHub 的 `::command::`） | 使用者字串一律以 `JSON.stringify` 等方式輸出，且不放在行首 |
| 測試框架的「只執行這個」（範例：`.only`）進入主分支 | 其他測試不執行卻顯示通過 | CI 中禁止（範例：Playwright `forbidOnly`）；設計沒寫時在交付摘要列出這項加嚴 |

### 3.2 時間與部署

- 「自工作流程開始 N 分鐘」的期限，以平台記錄的開始時間計算（範例：執行嘗試的 `run_started_at`），不要用某個 job 開始的時刻（會把排隊與前置步驟的時間算成餘裕）。重跑時以該次嘗試的開始時間為準。
- 靜態託管常有 CDN 快取（範例：回應帶 `max-age=600`）。輪詢部署結果時加上查詢字串避開快取；人工驗收時同樣可能看到舊版，回報設計或測試階段。

### 3.3 檢查腳本

- **讀 Markdown 時跳過程式碼區塊。** 範例文件常在 ``` 區塊中放示範用的標題與表格（範例：示範用的「變更紀錄」表）。
- **以表頭名稱找欄位，不用固定欄序。**
- **解析不到東西時失敗，不要視為零個而通過。** 範例：找不到某節、解析出零個必要編號。
- **完整比對識別碼。** `X-1` 不得被 `X-10` 或 `AX-1` 誤判；用前後界定（範例：`(?<![A-Za-z0-9-])X-1(?![0-9A-Za-z])`）。
- **路徑來自輸入時先驗證格式。** 範例：PR 說明中的 skill 名稱組成檔案路徑，先限制為 `[a-z0-9-]`。
- **多行規則逐列回報。** 錯誤訊息指出哪一列、期望值、實際值，方便作者修正。

### 3.4 靜態掃描測試名稱

用於「每個驗收編號都要有測試」這類檢查。

- **用 tokenizer，不要用整檔正規表示式。** 註解、字串、樣板字面值、正規表示式字面值的內容都不是程式碼；測試資料字串中的 `test('X-1 …')` 不得被採計。
- **前面接 `.` 的呼叫不是測試。** 範例：`/re/.test('X-1')`、子測試 `t.test(…)`。
- **名稱只採計單一字面值。** 字串串接、變數名稱無法靜態判定，不採計，並在介面說明中告訴測試 agent。
- **略過的寫法比想像多。** 除了 `test.skip(name)`、`describe.skip`、`{ skip }` 選項、略過區塊內的測試，還有：測試內呼叫 `test.skip()`／`test.fixme()`、`test.skip(條件)`（可能在區塊層級）、標註（範例：`annotation: { type: 'skip' }`）、子測試的 `t.skip()`／`t.todo()`。設計只列出部分寫法時，照設計實作並把遺漏的寫法列為設計問題；「不允許略過」生效前必須解決。

## 4. 單元測試

### 4.1 範圍

- 模組測試標準列出的每個行為與邊界各至少一個測試；把邊界清單逐項抄進測試名稱或註解，交付前逐項核對。
- 檢查腳本的外層（API、檔案）用模擬伺服器或暫存目錄跑一次完整流程（範例：本機 HTTP 伺服器模擬平台 API，檢查分頁讀取與最後寫入的內容）。
- 範本與檢查要互相測試：未填寫的範本必須被檢查判為失敗（證明範本沒有預填能通過的內容）。
- 平台設定檔（範例：工作流程 YAML）以靜態測試固定安全要求。正規表示式要錨定行首並先去除註解（範例：`statuses:` 含有 `uses:`、`package-manager-cache:` 含有 `cache:`）。

### 4.2 執行器

- 測試執行器的路徑參數以引號傳 glob（範例：Node.js 21 起位置參數視為 glob，傳目錄會失敗）。
- **glob 沒有匹配任何檔案時，執行器可能以 0 個測試「通過」**（範例：Node.js 22 `node --test 'no/match/**'` 結束代碼 0）。在交付摘要寫明哪些 glob 目前沒有檔案、由誰在何時補上。
- 端對端測試工具在沒有任何測試檔時通常以失敗結束（範例：Playwright「No tests found」）。基礎 PR 若由另一個 agent 稍後補上測試骨架，寫明這段期間 CI 預期失敗。

### 4.3 與驗收測試的分界

- 單元測試名稱與測試資料**不使用真實的驗收編號**，改用虛構編號（範例：`AC-ZZ-1`），避免編號覆蓋檢查誤把它當成驗收。
- 實作 agent 不寫端對端測試。需要在瀏覽器確認時，把暫用測試放在版本庫以外（範例：工作暫存目錄，連結 `node_modules` 以解析套件），用自訂設定檔指向它，驗證後刪除，不提交。

## 5. 本機驗證

| 項目 | 做法 |
|---|---|
| 安裝 | 依鎖定檔安裝；環境已預裝瀏覽器時沿用（範例：設定瀏覽器路徑的環境變數），不重新下載 |
| 建置 | 以指定的 commit 參數建置，檢查輸出 |
| 單元測試 | 全部執行 |
| 檢查腳本 | 對真實文件執行，核對解析結果與設計中的清單（數量與內容） |
| 工作流程 | YAML 解析、可取得時用 linter（範例：actionlint）；靜態安全測試 |
| 瀏覽器 | 暫用測試（第 4.3 節）在可用的引擎上執行 |
| 無法驗證 | 事件觸發、權限、平台設定、部署延遲：寫明由誰、在哪個步驟驗證 |

## 6. 給測試 agent 與審查 agent 的交接

- **介面說明：** 測試需要呼叫的函式（名稱、參數、回傳）、檔案位置、命名規則、檢查腳本如何辨識編號與略過、哪些寫法不會被辨識。
- **PR 說明：** 依範本填寫上工檢查、skill 版本號（讀 SKILL.md 變更紀錄最後一列）、作者與工作階段、對應編號、與設計不同之處。
- 修改 CI、檢查腳本、測試設定時，在 PR 說明逐項列出理由與「沒有降低任何檢查」的依據，供審查者核對。

## 7. 常見錯誤與改寫

| 錯誤寫法 | 問題 | 改寫（範例） |
|---|---|---|
| 以 `/test\(['"]([^'"]+)/g` 掃描整個測試檔 | 註解與測試資料字串中的呼叫也被採計 | tokenizer 只看程式碼 token |
| 單元測試寫 `test('X-5 的反例', …)` | 編號覆蓋檢查把單元測試當成驗收 | 用虛構編號 `AC-ZZ-5` |
| `actions/checkout`（寫入權杖事件）不指定 `ref` | 簽出 PR 目標分支 | 指定預設分支 |
| `uses: some/action@v4` | 標籤可被移動 | `uses: some/action@<40 碼 SHA> # v4.x.y` |
| `console.log('錯誤：' + userInput)` | 使用者字串可在行首形成工作流程指令 | `console.log('錯誤：' + JSON.stringify(userInput))` |
| 期限從部署 job 的第一步開始算 | 期限被放寬 | 以執行嘗試的開始時間計算 |
| 讀取 SKILL.md 中第一個「變更紀錄」表 | 讀到程式碼區塊中的範例 | 跳過程式碼區塊，取最後一個變更紀錄表 |
| 解析不到必要編號時印出「0 個缺漏」 | 檢查形同虛設 | 解析不到即以錯誤結束 |
| 靜態伺服器只擋 `..` 字面值 | 編碼過的 `/`（`%2f`）解碼後形成 `../` | 解碼後再解析路徑，確認仍在根目錄內 |
| 設計說「事件發生前採過渡規則」，事件已發生仍照過渡規則做範本 | 範本預填已失效的值，作者照抄即失敗 | 依「事件之後」的路徑，並回報設計 |

## 8. 自我審查清單

**輸入與範圍**
- [ ] 完成 agent-dev-workflow 上工檢查，輸入文件為已簽核的最新版
- [ ] 只實作本 PR 範圍；屬於測試 agent 的檔案沒有碰
- [ ] 設計的前提（例如其他 PR 是否已合併）都已與版本庫現況核對

**正確性**
- [ ] 每個判定邏輯都是純函式，並有單元測試
- [ ] 模組測試標準列出的邊界逐項有測試
- [ ] 單元測試名稱與資料不含真實驗收編號
- [ ] 範本與檢查互相測試過（未填寫的範本會失敗）
- [ ] 解析失敗時以錯誤結束，不會視為零個而通過

**CI 安全**
- [ ] `run:` 不插值使用者可控內容；以靜態測試固定
- [ ] 具寫入權杖的工作流程只簽出預設分支、不執行 PR 程式碼、不安裝、不快取
- [ ] 每個工作流程宣告最小權限；action 以 SHA 固定且輸入名稱已對照該版本
- [ ] 使用者字串不會在日誌行首輸出
- [ ] 沒有放寬任何檢查；加嚴之處已在交付摘要列出

**驗證與交接**
- [ ] 本機驗證的指令與結果已記錄；無法本機驗證的項目寫明由誰在何時驗證
- [ ] 沒有匹配檔案的 glob、預期失敗的 CI 已寫明原因與解除時點
- [ ] 給測試 agent 的介面說明含函式簽名、命名規則、不會被辨識的寫法
- [ ] 設計問題已依 agent-dev-workflow 5.1 列出
- [ ] 暫用測試與暫存檔沒有提交

## 9. 回饋機制

任何 agent 在實作、測試或審查時發現問題，依 agent-dev-workflow 第 7.3 節判斷是否為本 skill 的缺漏：

- 其他專案也可能發生、本 skill 沒有提醒 → 修改本 skill：加入規則，必要時加入第 7 節的「錯誤寫法／改寫」與第 8 節的檢查項，範例去除專案細節。
- 本 skill 有規定但沒有照做 → 不改規則；若規定容易漏看，改寫得更明確。
- 只與某專案有關 → 記在該專案文件，不改本 skill。

修改方式依 agent-dev-workflow 第 7.4 節：在下方變更紀錄寫明日期、發現的階段、問題、修改內容；不得為了讓目前的工作通過而刪除或放寬檢查；修改後以新規則重新檢查目前產出。版本庫建立後，本 skill 的修改與程式碼一樣經過 PR 與審查。
