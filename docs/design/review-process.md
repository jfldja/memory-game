## 1. 審查前的準備（審查 agent）

1. 以全新工作階段啟動，載入 agent-dev-workflow，完成上工檢查。
2. 只讀：PR 的差異與說明、docs/requirements.md、docs/design/（本文件、spec.md、module-test-standards.md、acceptance-test-plan.md）、docs/workflow.md。**不讀**作者 agent 的對話或推理過程（agent-dev-workflow 3.2）。
3. 確認自己的工作階段識別不在 PR 說明「作者」段落中（忽略大小寫比對，第 4 節第 2 步）。若相同，停止並回報統籌 agent（不得審查自己的變更）。PR 含多個角色的產出時，確認「作者」段落列出每個角色的工作階段；有 commit 的角色未列出時，判 R-1 不通過。
4. 記下 PR 目前的 head SHA（`gh pr view <n> --json headRefOid`）。審查期間若有新 commit，重新審查。

## 2. 審查紀錄格式

審查 agent 以 PR 對話區的**一般評論**留下（不是行內評論、也不是 GitHub 的 review 功能；後者在單一帳號下無法核准自己的 PR）。格式如下，第一行標記與「結果」「針對 commit」兩行由 `review-gate.mjs` 解析，必須逐字照寫：

```markdown
<!-- review-record v1 -->
## 審查紀錄

- 結果：APPROVED
- 針對 commit：3f9c2ab1e0d4c5b6a7980f1e2d3c4b5a69788776
- 審查者：審查 agent，工作階段 review-2026-11-05-pr2-a
- 作者：實作 agent，工作階段 impl-2026-11-05-pr2；測試 agent，工作階段 test-2026-11-05-pr2（照抄 PR 說明「## 作者」段落的全部工作階段）
- 獨立性：審查者與作者為同一模型（Claude）的不同工作階段（docs/workflow.md W-1）。審查者以全新上下文啟動，未讀作者的推理過程
- 審查依據：需求文件 v<版本>；軟體規格書 v<版本>；審查清單 v<版本>
- 已載入 skill：agent-dev-workflow <版本>；software-design-phase <版本>；requirements-spec <版本>（填版本庫內各 SKILL.md 變更紀錄最後一列的版本號。skill 副本已隨 PR-1 同步，agent-dev-workflow 與 requirements-spec 都有變更紀錄，不再填「無版本號」；DQ-6、spec.md 12.4）

### 逐項結果

| 編號 | 項目 | 結果 | 說明 |
|---|---|---|---|
| R-1 | PR 說明含上工檢查與正確的 skill 版本號 | 通過 | |
| R-2 | PR 說明的對應編號完整 | 通過 | |
（範例省略 R-3～R-15；實際紀錄 R-1～R-15 各恰好一列。「不適用」的列在說明欄寫理由，例：`| R-5 | 狀態機變更與 spec.md 第 5 節一致 | 不適用 | 本 PR 沒有 core/game.js |`）

### 發現的問題

（無；或逐條列出：位置、問題、對應編號、嚴重度、建議）
```

規則（第 3 輪審查 M-2 起為**白名單**：`review-gate.mjs` 只接受下列格式，任何一處不符即整則紀錄無效，判定 `failure`，不嘗試解讀；第 4 節第 5 步）：

- **字元：** 全文不得含零寬或其他不可見格式字元（Unicode 類別 Cf，例：U+200B～U+200F、U+202A～U+202E、U+2060～U+2064、U+FEFF），也不得含換行、定位字元以外的控制字元。
- **欄位行：** 「結果」「針對 commit」「審查者」三個欄位各恰好一行，寫法逐字為 `- 結果：<值>`、`- 針對 commit：<值>`、`- 審查者：<說明>，工作階段 <識別>`（半形連字號、一個空格、全形冒號；不加粗體或其他符號）。同一欄位出現兩行以上（即使寫法不同，例如另有一行 `**結果**：…`、`> - 結果：…`）即無效；「看似某欄位的行」以第 4 節的「偵測形式」判斷。
- **表格：** 全文只能有一個表格，即「逐項結果」表：表頭逐字為 `| 編號 | 項目 | 結果 | 說明 |`，接分隔列，之後每一列恰好 4 格，第一格逐字為半形 `R-<數字>`（不加粗體、不加括號說明、不用全形）。「發現的問題」等其他內容一律用條列，不得用表格。
- **項目：** R-1～R-15 各恰好一列，不得有清單以外的編號。
- 「結果」只能是 `APPROVED` 或 `CHANGES_REQUESTED`。任一項為「不通過」時只能是 `CHANGES_REQUESTED`。
- 「針對 commit」必須是完整 40 碼 SHA。
- 每一項審查清單**恰好一列**，結果欄只寫「通過」「不通過」「不適用」三者之一（不加其他文字；說明寫在說明欄），「不適用」須在說明欄寫理由。同一 R 編號寫兩列以上時，整則紀錄無效（第 4 節第 5 步），需要更正時留一則新的紀錄。
- 工作階段識別由統籌 agent 在派工時指定，格式建議 `<角色>-<日期>-<PR 或工作>-<序號>`，**只能使用半形小寫英數字與連字號**（第 3 輪審查 M-2 起由檢查強制：去除前後空白、NFKC、轉小寫後須符合 `^[a-z0-9-]+$`，否則無效；作者段落由 `pr-body` 檢查，審查者由 `review-gate` 檢查）；只要同一 PR 內可區分即可。只差大小寫或全半形的兩個識別碼視為同一個工作階段。
- 紀錄留下後不要編輯；需要更正時留一則新的紀錄（判定以最後一則為準）。
- **渲染相關的禁止構造（v0.6.1，DQ-14 (b)；4.1 X1～X7、T3、T4）：** 全文不得含字元參照（`&#…;`、`&#x…;`、`&<英文名稱>;`，**包括寫在程式碼中**；需要提到時以文字描述，例：「『結』字的十六進位字元參照」）、Unicode 的 Default_Ignorable_Code_Point（例：U+3164、U+FFA0、U+034F、變體選擇符，含 emoji 的 U+FE0F）、結合符號、U+2800；第 1 行以外不得有 `<!`、`<?`（HTML 註解、宣告、CDATA、處理指令）；HTML 標籤必須在同一行內結束（散文中的 `a<b` 也算，改寫為 `a < b`）；逐項結果表最後一列的下一行必須是空行；全文只能有逐項結果表一個分隔列（「發現的問題」不得貼出表格範例，含程式碼區塊中）。欄位名稱以簡體字寫（例：`- 结果：…`）也算該欄位的一行。

## 4. 審查檢查的判定規則（`scripts/review-gate.mjs`）

輸入：版本庫、PR 編號（`pull_request_target` 取自事件；`issue_comment` 取自 `github.event.issue.number`，且只處理 `github.event.issue.pull_request` 存在的事件）。

**偵測形式（v0.5.1；DQ-13 採 (b)，產品負責人 2026-11-10 16:47 決定）：** 第 3 步與第 5 步第 1 項用來「找出看似某欄位的行」與「找出表格列」的正規化。偵測形式只用來找出這些行，**合法與否一律以原文逐字比對第 2 節的寫法**（不變）。以下「字母」指 Unicode 一般類別 L（含中日韓文字），「ASCII 標點」指 U+0021～U+002F、U+003A～U+0040、U+005B～U+0060、U+007B～U+007E。

**欄位偵測形式 `fieldForm(行)`：** 對每一行依序套用 F1～F9，整個流程只套用一次；F2、F3 各自重複到結果不再改變（不動點），其餘步驟一次即達不動點。

| 步驟 | 動作（確切範圍） | 為什麼 |
|---|---|---|
| F1 | Unicode NFKC | 全形冒號成為半形 `:`、全形英數與全形 `｜`、`（` `）` 成為半形 |
| F2（v0.6.1 起為 F2′） | 刪除 `<!--`、`-->` 兩種分隔符號（保留其間的文字），以及依 CommonMark 文法的完整 HTML 標籤：開始標籤 `<[A-Za-z][A-Za-z0-9-]*(?:\s+[A-Za-z_:][A-Za-z0-9_.:-]*(?:\s*=\s*(?:[^\s"'=<>`]+\|'[^']*'\|"[^"]*"))?)*\s*\/?>`、結束標籤 `<\/[A-Za-z][A-Za-z0-9-]*\s*>`。重複到不動點。（v0.5.1～v0.6 為 `<\/?[A-Za-z][^<>]*>`，引號中含 `>` 的屬性會留下殘段，4.1 D3） | 讓藏在註解中的欄位行與被標籤包住的欄位名（`<b>結果</b>：`）被偵測到。只刪分隔符號而不刪註解內容，所以跨行的註解每一行都照樣偵測（含註解的紀錄另由 X6 判為無效）。`<版本>` 這類 `<` 後接非 ASCII 字母的佔位文字不是標籤，不刪；不符合文法的「標籤」（例：`<b !>`）不刪，該行由 X7 判為無效 |
| F3 | 把連結與圖片 `[文字](網址)`、`![文字](網址)` 換成「文字」（正規表示式 `!?\[([^\[\]]*)\]\([^()]*\)` → `$1`）。重複到不動點 | `[結果](…)：` 渲染後讀者看到「結果：」 |
| F4 | 刪除緊接在 ASCII 標點之前的反斜線 | `\- 結果：` 渲染為「- 結果：」 |
| F5 | 刪除 `*`、`_`、`` ` ``、`~` 與所有空白字元（`\s`） | 強調、程式碼、刪除線符號與空白不改變讀者看到的欄位名 |
| F6 | 刪除行內任何位置的核取方塊 `[]`、`[x]`、`[X]`（F5 已刪除其中的空白） | 工作清單 `- [ ] 結果：`。放在 F7 之前，因為 `x` 是字母，F7 不會刪它 |

- 權限：`statuses: write`、`pull-requests: read`、`issues: read`、`contents: read`。
- 只簽出預設分支（`actions/checkout` 在 `pull_request_target`／`issue_comment` 下預設即簽出預設分支），**不簽出、不執行 PR 的程式碼**；不執行 `npm install`、不使用 `actions/cache`；腳本只用 Node.js 內建模組。

- **T3：** 逐項結果表（表頭、分隔列與連續的 R 列，即 T1、T2 判定的連續表格列）最後一列的下一行，必須符合 `^[ \t]*$` 或不存在；否則「表格格式不符：第 n 行」（n 為下一行）。理由：GFM 表格延續到空行或另一個區塊開始為止，緊接的任何一行都會成為表格的一列（4.1 表 A1～A4b、C10）；只含 U+00A0 或 U+3164 的行不是空行。不以「另一個區塊開始」為例外，因為要模擬 GFM 的區塊開始條件。
- **T4：** 逐項結果表分隔列（表頭的下一行）以外，任何一行去除所有 `\s` 後符合 `^(?:>|[-+*]|[0-9]{1,9}[.)])*[|:-]+$`，且含 `-`，並含 `|` 或 `:` 時，「表格格式不符：第 n 行」。這是任何容器（引用、清單項目）中 GFM 分隔列寫法的超集；沒有第二個分隔列就沒有第二個表格（A9：`:-:` 構成單欄表格）。`- - -`（分隔線）、`12:30-13:00`（數字只能是清單編號）不符合。全文沒有表格時，T4 對每一行判定（之後因缺項而無效）。

**檢查順序（`validateRecord`，回報第一個成立的原因）：** X1 → X2 → X3 → X4 → X5 → X6（逐行）→ X7（逐行）→ 第 1 行標記 → 欄位行（F1～F9）→ 表格列（T1、T2 的連續性與逐字格式）→ T3 → T4 → R 列的重複、缺項、清單外、結果值、「不適用」理由 → 審查者識別格式。**候選的判定（`isCandidateFor`，v0.6.1 修改）：** 第一行為標記、作者為受信任的協作者，且**原文任何位置**含最新 head 的完整 40 碼 SHA（不分大小寫）即為候選，不再要求該 SHA 出現在偵測形式以「針對commit:」開頭的行。理由：F2′ 不刪不合文法的標籤，若沿用偵測形式，`- <b !>針對 commit</b>：<SHA>` 這種較晚的紀錄在 PR-1c 版不再是候選，較早的有效紀錄會因此生效，與「只增加無效」矛盾（設計 agent 寫入正文時發現）；改為原文含 SHA 後，候選集合是 PR-1b 版的超集，較晚的候選只會使判定變為無效（之後的白名單檢查與「針對 commit 等於 head」照舊）。

## 5. 已知限制

- CI 只能確認紀錄存在且格式正確，無法確認審查真的做過（需求第 9 節已接受）。產品負責人在 UAT 前抽看（AC-EQ-5）。
- 工作階段識別由 agent 自行填寫，CI 無法驗證真偽。
- 有寫入權限者可以直接以 API 寫入 `review-record` 狀態；分支保護指定來源為 GitHub Actions 可擋下以個人權杖寫入的狀態。
- 機械檢查只能證明驗收測試有執行斷言，不能證明斷言驗證了驗收標準；這部分由 R-15 與變異檢查把關（spec.md 12.2.1「殘餘風險」）。
- 第一個 PR（加入本機制的 PR）不受本檢查把關，由產品負責人人工確認；`review-record` 在 PR-1 之後的第一個 PR（**PR-1b**，v0.5；原為 PR-2）寫入過一次後、合併前加為必要檢查（spec.md 12.6 步驟 4、6b、8；DQ-8 已由產品負責人接受，處理方式見 spec.md 12.6「EQ-2 啟動例外的處理」；main 上的 review-gate 無法寫入狀態時，不論是第一次執行或之後的版本，見 DQ-11）。
- 本檢查永遠以預設分支上的 `review-gate.mjs` 判定。修改本檢查的 PR 由修改前的版本判定，修改在合併後才生效：PR-1b（實作 v0.5、v0.5.1 的第 4 節）由 PR-1 版判定；PR-1c（實作 DQ-14 (b)，v0.6 新增）由 PR-1b 版判定。處理方式都是新版 `--dry-run` 試算＋人工確認清單（spec.md 12.6「PR-1b 由舊版判定」「PR-1c 由 PR-1b 版判定」）。v0.6 起（產品負責人 2026-11-10 21:37 同意），PR-1b 版不做步驟 8b；PR-1c 合併後開**一次**探測 PR B，觀察最終版本在平台上的第一次執行（spec.md 12.6 步驟 8b）。
