## 1. 審查前的準備（審查 agent）

1. 以全新工作階段啟動，載入 agent-dev-workflow，完成上工檢查。
2. 只讀：PR 的差異與說明、docs/requirements.md、docs/design/（本文件、spec.md、module-test-standards.md、acceptance-test-plan.md）、docs/workflow.md。**不讀**作者 agent 的對話或推理過程（agent-dev-workflow 3.2）。
3. 確認自己的工作階段識別不在 PR 說明「作者」段落中（忽略大小寫比對，第 4 節第 2 步）。若相同，停止並回報統籌 agent（不得審查自己的變更）。PR 含多個角色的產出時，確認「作者」段落列出每個角色的工作階段；有 commit 的角色未列出時，判 R-1 不通過。
4. 記下 PR 目前的 head SHA（`gh pr view <n> --json headRefOid`）。審查期間若有新 commit，重新審查。

## 2. 審查紀錄格式

審查 agent 以 PR 對話區的**一般評論**留下（不是行內評論、也不是 GitHub 的 review 功能；後者在單一帳號下無法核准自己的 PR）。格式如下，第一行標記與「結果」「針對 commit」兩行由 `review-gate.mjs` 解析，必須逐字照寫：

```markdown
<!-- review-record v1 -->
## 審查紀錄

- 結果：APPROVED
- 針對 commit：3f9c2ab1e0d4c5b6a7980f1e2d3c4b5a69788776
- 審查者：審查 agent，工作階段 review-2026-11-05-pr2-a
- 作者：實作 agent，工作階段 impl-2026-11-05-pr2；測試 agent，工作階段 test-2026-11-05-pr2（照抄 PR 說明「## 作者」段落的全部工作階段）
- 獨立性：審查者與作者為同一模型（Claude）的不同工作階段（docs/workflow.md W-1）。審查者以全新上下文啟動，未讀作者的推理過程
- 審查依據：需求文件 v<版本>；軟體規格書 v<版本>；審查清單 v<版本>
- 已載入 skill：agent-dev-workflow <版本>；software-design-phase <版本>；requirements-spec <版本>（填版本庫內各 SKILL.md 變更紀錄最後一列的版本號。skill 副本已隨 PR-1 同步，agent-dev-workflow 與 requirements-spec 都有變更紀錄，不再填「無版本號」；DQ-6、spec.md 12.4）

### 逐項結果

| 編號 | 項目 | 結果 | 說明 |
|---|---|---|---|
| R-1 | PR 說明含上工檢查與正確的 skill 版本號 | 通過 | |
| R-2 | PR 說明的對應編號完整 | 通過 | |
（範例省略 R-3～R-15；實際紀錄 R-1～R-15 各恰好一列。「不適用」的列在說明欄寫理由，例：`| R-5 | 狀態機變更與 spec.md 第 5 節一致 | 不適用 | 本 PR 沒有 core/game.js |`）

### 發現的問題

（無；或逐條列出：位置、問題、對應編號、嚴重度、建議）
```

規則（第 3 輪審查 M-2 起為**白名單**：`review-gate.mjs` 只接受下列格式，任何一處不符即整則紀錄無效，判定 `failure`，不嘗試解讀；第 4 節第 5 步）：

- **字元：** 全文不得含零寬或其他不可見格式字元（Unicode 類別 Cf，例：U+200B～U+200F、U+202A～U+202E、U+2060～U+2064、U+FEFF），也不得含換行、定位字元以外的控制字元。
- **欄位行：** 「結果」「針對 commit」「審查者」三個欄位各恰好一行，寫法逐字為 `- 結果：<值>`、`- 針對 commit：<值>`、`- 審查者：<說明>，工作階段 <識別>`（半形連字號、一個空格、全形冒號；不加粗體或其他符號）。同一欄位出現兩行以上（即使寫法不同，例如另有一行 `**結果**：…`、`> - 結果：…`）即無效；「看似某欄位的行」以第 4 節的「偵測形式」判斷。
- **表格：** 全文只能有一個表格，即「逐項結果」表：表頭逐字為 `| 編號 | 項目 | 結果 | 說明 |`，接分隔列，之後每一列恰好 4 格，第一格逐字為半形 `R-<數字>`（不加粗體、不加括號說明、不用全形）。「發現的問題」等其他內容一律用條列，不得用表格。
- **項目：** R-1～R-15 各恰好一列，不得有清單以外的編號。
- 「結果」只能是 `APPROVED` 或 `CHANGES_REQUESTED`。任一項為「不通過」時只能是 `CHANGES_REQUESTED`。
- 「針對 commit」必須是完整 40 碼 SHA。
- 每一項審查清單**恰好一列**，結果欄只寫「通過」「不通過」「不適用」三者之一（不加其他文字；說明寫在說明欄），「不適用」須在說明欄寫理由。同一 R 編號寫兩列以上時，整則紀錄無效（第 4 節第 5 步），需要更正時留一則新的紀錄。
- 工作階段識別由統籌 agent 在派工時指定，格式建議 `<角色>-<日期>-<PR 或工作>-<序號>`，**只能使用半形小寫英數字與連字號**（第 3 輪審查 M-2 起由檢查強制：去除前後空白、NFKC、轉小寫後須符合 `^[a-z0-9-]+$`，否則無效；作者段落由 `pr-body` 檢查，審查者由 `review-gate` 檢查）；只要同一 PR 內可區分即可。只差大小寫或全半形的兩個識別碼視為同一個工作階段。
- 紀錄留下後不要編輯；需要更正時留一則新的紀錄（判定以最後一則為準）。
- **v0.6：** 字元參照、Default_Ignorable_Code_Point、HTML 註解、表後沒有空行等寫法是否另外判為無效，依 DQ-14 決定（4.1）；決定前維持本節規則。

## 4. 審查檢查的判定規則（`scripts/review-gate.mjs`）

輸入：版本庫、PR 編號（`pull_request_target` 取自事件；`issue_comment` 取自 `github.event.issue.number`，且只處理 `github.event.issue.pull_request` 存在的事件）。

**偵測形式（v0.5.1；DQ-13 採 (b)，產品負責人 2026-11-10 16:47 決定）：** 第 3 步與第 5 步第 1 項用來「找出看似某欄位的行」與「找出表格列」的正規化。偵測形式只用來找出這些行，**合法與否一律以原文逐字比對第 2 節的寫法**（不變）。以下「字母」指 Unicode 一般類別 L（含中日韓文字），「ASCII 標點」指 U+0021～U+002F、U+003A～U+0040、U+005B～U+0060、U+007B～U+007E。

**欄位偵測形式 `fieldForm(行)`：** 對每一行依序套用 F1～F8，整個流程只套用一次；F2、F3 各自重複到結果不再改變（不動點），其餘步驟一次即達不動點。

| 步驟 | 動作（確切範圍） | 為什麼 |
|---|---|---|
| F1 | Unicode NFKC | 全形冒號成為半形 `:`、全形英數與全形 `｜`、`（` `）` 成為半形 |
| F2 | 刪除 `<!--`、`-->` 兩種分隔符號（保留其間的文字），以及 HTML 標籤：`<`、可選的 `/`、一個 ASCII 字母、之後任意個非 `<`、`>` 的字元、`>`（正規表示式 `<!--` ｜ `-->` ｜ `<\/?[A-Za-z][^<>]*>`）。重複到不動點 | 讓藏在註解中的欄位行與被標籤包住的欄位名（`<b>結果</b>：`）被偵測到。只刪分隔符號而不刪註解內容，所以跨行的註解每一行都照樣偵測。`<版本>` 這類 `<` 後接非 ASCII 字母的佔位文字不是標籤，不刪 |
| F3 | 把連結與圖片 `[文字](網址)`、`![文字](網址)` 換成「文字」（正規表示式 `!?\[([^\[\]]*)\]\([^()]*\)` → `$1`）。重複到不動點 | `[結果](…)：` 渲染後讀者看到「結果：」 |
| F4 | 刪除緊接在 ASCII 標點之前的反斜線 | `\- 結果：` 渲染為「- 結果：」 |
| F5 | 刪除 `*`、`_`、`` ` ``、`~` 與所有空白字元（`\s`） | 強調、程式碼、刪除線符號與空白不改變讀者看到的欄位名 |
| F6 | 刪除行內任何位置的核取方塊 `[]`、`[x]`、`[X]`（F5 已刪除其中的空白） | 工作清單 `- [ ] 結果：`。放在 F7 之前，因為 `x` 是字母，F7 不會刪它 |
| F7 | 刪除行首最長的一段「非字母」字元（正規表示式 `^[^\p{L}]+`，含數字、標點、符號與直線）。一次刪除最長前綴，等同重複到不動點 | 涵蓋 v0.5.1 的引用、清單、有序清單、標題符號，以及 `•`、`・`、`–`、`1、`、`(1)`（F1 後）、`1.`、`1)` 等任何非字母前綴，不再逐一列舉 |
| F8 | 英文轉小寫 | `針對 Commit：` 也算 |

標籤以 F8 的結果比對開頭：`結果:`、`針對commit:`、`審查者:`。

**表格列偵測 `isTableLine(行)`：** 下列任一成立即為表格列：
- T1：F1 之後的行含 HTML 表格標籤，即 `<`、可選的 `/`、`table`、`thead`、`tbody`、`tr`、`td` 或 `th`（不分大小寫）、之後為非字母數字字元或行尾。理由：渲染後就是第二個表格，第 2 節「全文只能有一個表格」本來就不允許；這類行的原文必然不符 R 列格式，因此整則無效。
- T2：F1、F2 之後去除前後空白，再刪除行首最長的一段「非字母且不是 `|`」的字元（正規表示式 `^[^\p{L}|]+`；引用 `>`、清單 `-`、有序清單編號、`•` 等皆在範圍內），結果以 `|` 開頭。

表格列的**原文**必須是第 2 節允許的表頭、分隔列或 R 列，且所有表格列必須連續；所以引用區塊、清單項目中的表格列與 HTML 表格都使整則「表格格式不符」。

**20 種寫法的判定（設計 agent 以 (b) 的參考實作、在第 2 節合法範本上逐一加入一行實測，2026-11-10）：**

| 加入的一行 | v0.5.1 初版（PR-1b commit 54bc2a5） | (b) | 原因 |
|---|---|---|---|
| （不加，合法範本） | 有效 | 有效 | 三個欄位行各偵測一次；表格合法 |

**仍維持有效的寫法與理由：** 「發現的問題」以條列寫出某一項的問題（例：`- R-5：狀態機少了 T-11 的守衛，不通過的原因…`）是第 2 節允許、也是審查者需要的寫法；把「條列中含 R 編號與『不通過』」判為無效會誤判合法紀錄，所以不在 (b) 的範圍。這類行不是欄位行，也不是表格列，review-gate 不讀它；若逐項表與條列矛盾（表中 R-5 通過、條列寫 R-5 不通過），由 R 列判定，矛盾由產品負責人抽查（AC-EQ-5）發現。其他殘餘：F7 只刪「非字母」前綴，所以以字母開頭的前綴（例：`備註結果：…`、`a. 結果：…`）不被算成欄位行；這類寫法讀者也不會把它讀成「結果」欄位，接受。

**不會使合法紀錄無效的回歸檢查（2026-11-10 實測）：** 第 2 節範本（補齊 R-1～R-15，佔位 `v<版本>` 保留）：三個欄位行各偵測一次，沒有其他行被算成欄位行或表格列。PR #2（探測 PR A）的實際審查紀錄（2026-11-10 08:33，R-1～R-14，結尾含 Markdown 連結 `[Claude Code](…)`）：三個欄位行各偵測一次、表格連續且合法；補上 R-15 一列後，現行 `validateRecord` 判定有效，(b) 沒有增加任何被偵測的行，所以 (b) 下同樣有效。

步驟：

1. 以 API 重新讀取 PR：最新 head SHA、PR 說明、狀態。PR 已關閉時結束，不寫狀態。
2. 從 PR 說明「## 作者」段落取出所有工作階段識別：段落內每一行符合 `工作階段：<識別>`（全形冒號，去除前後空白與 HTML 註解）者都採計；一個 PR 可有多位作者（例如「- 角色：實作 agent」「- 工作階段：…」兩行一組重複）。**比對規則（v0.5，PR-1 審查 N-1；第 3 輪審查 M-2）：** 作者與審查者的工作階段識別都先去除前後空白、做 Unicode NFKC 正規化（全形英數轉半形）、再轉小寫；正規化後**必須符合 `^[a-z0-9-]+$`**，否則 `failure`「工作階段識別格式不符」；之後才比對是否相同。理由：識別碼由 agent 自行填寫，`IMPL-1` 與 `impl-1`、全形與半形顯然指同一個工作階段；區分大小寫會讓審查者只改大小寫就通過「審查者不等於作者」的檢查。NFKC 不會移除零寬字元（實測 U+200B 保留），也不會把相似字（例：西里爾字母 і）轉成拉丁字母，所以另以字元集限定排除這兩類。
3. 讀取 PR 的全部一般評論，篩選：
   - 第一行為 `<!-- review-record v1 -->`；
   - `author_association` 為 `OWNER`、`MEMBER` 或 `COLLABORATOR`（公開版本庫任何人都能評論）；
   - 「針對 commit」等於最新 head SHA。判定「是否針對最新 head」時，凡是**偵測形式**（本節「偵測形式」）以「針對commit:」開頭的行，只要任何一行含最新 head 的完整 SHA，該則就是候選（即使欄位重複或寫法不符）；這樣格式錯誤的較晚紀錄不會被略過而讓較早的紀錄生效。
4. 取符合條件的**最後一則**（依建立時間）。最後一則無效時判定 `failure`，**不退回**採用較早的紀錄；更正方式是再留一則新的紀錄。沒有時：狀態 `failure`，說明「沒有針對 <短碼> 的審查紀錄」。
5. 檢查該則，依序（回報第一個成立的原因）：
   1. **格式白名單（第 3 輪審查 M-2）：** 依第 2 節「規則」逐項檢查，任何一處不符即 `failure`，說明寫出第一個不符之處：「含不可見字元」「欄位重複或格式不符：<欄位>」「表格格式不符：第 n 行」「審查清單重複：R-n」「審查清單缺項：R-n」「清單以外的項目：R-n」「結果值不符：R-n」「不適用未寫理由：R-n」「工作階段識別格式不符」。判斷「欄位重複」時，凡**偵測形式**以「結果:」「針對commit:」「審查者:」開頭的行都算該欄位的一行；該欄位必須恰好一行，且那一行的**原文**逐字符合第 2 節的寫法。判斷「表格列」時，以本節的 `isTableLine`（T1、T2）判斷（全形 `｜`、引用區塊與清單項目中的表格列、HTML 表格都算），每一列的**原文**都必須是第 2 節允許的表頭、分隔列或 R 列（以 `>`、`-` 開頭或含 HTML 的列必然不符）。
      - **重複（v0.5，PR-1 審查 N-1）：** 同一 R 編號出現兩列以上時整則無效，不以第一列或最後一列為準。理由：以最後一列為準時，「不通過」可被同編號後一列的「通過」覆蓋；任一列為準都會讓自相矛盾的紀錄得到其中一種解讀，判定無效最單純，更正方式是留一則新的紀錄。同理，欄位行重複（例：先 `- 結果：APPROVED`、後 `- 結果：CHANGES_REQUESTED`）也整則無效（第 3 輪審查 M-2 (b)）。
      - **看似 R 列卻不符格式的列**（例：`| **R-5** | … | 不通過 |`、`| Ｒ－５ | … |`、`| R-5（補充） | … |`）整則無效（第 3 輪審查 M-2 (a)）。舊版只採計 `^R-\d+$` 的列、忽略其他列，所以這類列中的「不通過」會被同編號的正規列覆蓋。
      - 任一 R 列中，第 1～2、4 格去除 Markdown 強調符號與空白後恰為「不通過」時（例：結果寫錯欄），同樣判定「表格格式不符」。
   2. 「審查者」的工作階段識別不等於第 2 步任何作者的工作階段（比對規則見第 2 步）；否則 `failure`「審查者與作者相同或未標明」。PR 說明中任一作者識別格式不符時 `failure`「作者工作階段識別格式不符」。
   3. 含「同一模型」與「不同工作階段」字樣；否則 `failure`「未註明 W-1」。
   4. **不通過：** 任一 R 列結果為「不通過」，或「結果」不是 `APPROVED`，`failure`「審查要求修改」。
6. 全部通過：`success`，說明「已審查 <短碼>（審查者 <工作階段>）」。
7. 以 `POST /repos/{owner}/{repo}/statuses/{head_sha}` 寫入，`context` 為 `review-record`，`target_url` 指向該則評論（或 PR）。

工作流程設定：

- 權限：`statuses: write`、`pull-requests: read`、`issues: read`、`contents: read`。
- 只簽出預設分支（`actions/checkout` 在 `pull_request_target`／`issue_comment` 下預設即簽出預設分支），**不簽出、不執行 PR 的程式碼**；不執行 `npm install`、不使用 `actions/cache`；腳本只用 Node.js 內建模組。
- **不得把事件內容插值到 `run:`**（評論內容、PR 標題與說明、`head.ref` 等皆為使用者可控字串，插值會造成指令注入）。PR 編號以 `env: PR_NUMBER: ${{ github.event.pull_request.number || github.event.issue.number }}` 傳入，其餘一律由腳本經 API 讀取。
- 並行群組：`group: review-gate-${{ github.event.pull_request.number || github.event.issue.number }}`、`cancel-in-progress: false`。同一 PR 的執行依序進行，每次都重新讀取最新 head SHA 與全部評論，所以最後完成的執行依最新狀態寫入（commit status 對同一 context 以最後寫入為準）。

`review-gate.mjs` 的判定邏輯寫成純函式 `evaluate({ headSha, prBody, prUrl, comments }) → { state, description, targetUrl }`，由實作 agent 撰寫單元測試；API 呼叫只在外層薄包裝中。`prUrl`（選用，v0.5.1 補入簽名）是 PR 的網址，沒有候選紀錄時作為 `targetUrl`（第 7 步「或 PR」）；有候選紀錄時 `targetUrl` 為該則評論的網址。另提供 `--dry-run`（第 3 輪審查 M-3；spec.md 12.6）：以 API 讀取指定 PR 的資料、呼叫同一個 `evaluate`、只印出 PR 狀態（open／closed）、head SHA、判定與原因，不寫入任何狀態；在 PR 分支上執行時，可用尚未合併的新版判定真實資料。v0.5.1 釐清（實作的選擇，設計採用）：
- **PR 已關閉時仍試算。** 第 1 步「PR 已關閉時結束，不寫狀態」只適用於寫入模式；`--dry-run` 不寫入，對已關閉的 PR 試算沒有副作用，可用來事後核對（例：關閉後的探測 PR A、合併後的 PR-1b）。輸出含 PR 狀態，貼作證據時可辨識。
- **權杖可省略。** 只讀公開版本庫的 PR 與評論；省略時受未驗證的 API 次數限制。寫入模式仍必須有權杖。

**DQ-14 的選項（決定前不實作；每個選項都寫到可直接展開為正文的程度）：**

**(a) 依 GFM 規格模擬渲染，重寫偵測。** 偵測前依序：(a1) 解碼字元參照（十進位、十六進位與 HTML5 的 2,231 個具名參照；具名參照表以 WHATWG `entities.json` 為來源存成資料檔）；但程式碼區段與程式碼區塊內不解碼，需依 CommonMark 規則辨識反引號串與圍欄；(a2) 刪除 Default_Ignorable_Code_Point 與 U+2800；(a3) 刪除同一行內完整的 HTML 註解（含內容）、處理指令、宣告、CDATA，標籤改用 CommonMark 6.6 的標籤文法，跨行的標籤先接成一行；(a4) 表格範圍依 GFM：在每個容器（引用、清單項目）內辨識分隔列，表格延續到空行或另一個區塊開始（ATX 標題、圍欄、引用、清單項目、分隔線、HTML 區塊的 7 種開始條件），全文的表格數與每一列都要與合法逐項表一致；(a5) 欄位名稱另對應簡體字。**誤判：** 最低，合法紀錄的寫法不受限制，PR #3 的實際紀錄（程式碼中寫了字元參照）仍有效。**成本：** 高。需實作 CommonMark 區塊結構與程式碼區段的子集、內嵌約 30 KB 的具名參照表；單元測試要以 cmark-gfm 的渲染結果作為對照資料（CI 不能安裝套件，資料由設計或測試 agent 預先產生並提交）。**殘餘風險：** 模擬不完整的部分（GFM 或 GitHub sanitizer 的細節、日後的版本差異）會成為新的繞過，而且不容易被發現。

**(b) 正規化前先拒絕，再加兩條表格邊界規則（建議）。** 在第 2 節「規則」與第 4 節第 5 步第 1 項加入下列檢查，任何一項成立即整則無效（依序回報第一個成立者）；偵測形式另做兩處修改：
- X1（現行）：含 Cf 或換行、定位字元以外的控制字元 →「含不可見字元」。
- X2：含 Unicode 性質 Default_Ignorable_Code_Point 的字元（含 U+115F、U+1160、U+3164、U+FFA0、U+034F、U+180B～U+180F、U+FE00～U+FE0F、U+E0000～U+E0FFF；JavaScript `\p{Default_Ignorable_Code_Point}`）→「含不可見字元」。
- X3：含結合符號（一般類別 M，`\p{M}`）→「含不可見字元」。理由：紀錄只用正體中文與 ASCII，沒有需要結合符號的寫法；結合符號可以疊在欄位名稱上而不改變讀者的讀法。
- X4：含 U+2800（點字空白，渲染為空白但不屬於 `\s`）→「含不可見字元」。
- X5：原文含字元參照，即正規表示式 `&(?:#[0-9]+|#[xX][0-9A-Fa-f]+|[A-Za-z][A-Za-z0-9]*);`（不論是否在程式碼中、是否為有效的具名參照）→「含字元參照」。
- X6：第 1 行以外的任何一行含 `<!` 或 `<?`（HTML 註解、宣告、CDATA、處理指令）→「含 HTML 註解或宣告：第 n 行」。
- X7：一行刪除所有完整的開始與結束標籤（F2′ 的文法）後，仍含 `<` 後接 ASCII 字母或 `/` 後接 ASCII 字母 →「HTML 標籤未在同一行結束：第 n 行」。
- F2′：F2 的標籤改用 CommonMark 6.6 的文法：開始標籤 `<[A-Za-z][A-Za-z0-9-]*(?:\s+[A-Za-z_:][A-Za-z0-9_.:-]*(?:\s*=\s*(?:[^\s"'=<>`]+|'[^']*'|"[^"]*"))?)*\s*\/?>`、結束標籤 `<\/[A-Za-z][A-Za-z0-9-]*\s*>`（引號中的 `>` 屬於屬性值）。`<!--`、`-->` 的刪除不變（X6 已使含註解的紀錄無效，F2 對註解的處理只影響 `isCandidateFor`）。F2′ 單獨使用時，F2 原本會刪除的非法「標籤」（例：`<b !>`）會留在偵測形式中，使該行不再被偵測為欄位行；這類行必然被 X7 判為無效，所以 F2′ 與 X7 合起來只增加無效的情況。
- F9：F8 之後把 `结`、`针`、`对`、`审` 分別換成 `結`、`針`、`對`、`審`，讓簡體或簡繁混用的欄位名稱也被偵測。
- T3：逐項表最後一列的下一行必須是空行（只含空格與定位字元，`^[ \t]*$`）或沒有下一行 →「表格格式不符：第 n 行」。理由：GFM 表格延續到空行；只含 U+00A0、U+3164 的行不是空行。
- T4：除了逐項表的分隔列，任何一行去除所有空白（`\s`）後符合 `^(?:>|[-+*]|[0-9]{1,9}[.)])*[|:-]+$`，且含 `-` 並含 `|` 或 `:` →「表格格式不符：第 n 行」。這是任何容器中 GFM 分隔列的超集（前綴為引用與清單符號）；沒有第二個分隔列，就沒有第二個表格。`12:30-13:00` 這類行不符合（數字只能是清單編號）。
- 作者段落（spec.md 12.4、`check-pr-body.mjs`，依 DQ-14 附帶問題決定）：「## 作者」段落中，偵測形式（F1～F9）以 `工作階段:` 開頭的行，原文必須符合 `^\s*(?:[-*]\s+)?工作階段：(.*)$`，否則 `pr-body` 失敗「作者段落格式不符：第 n 行」，review-gate 的作者解析同樣失敗「作者工作階段識別格式不符」；X2～X5 同樣套用於該段落（先依現行做法移除 HTML 註解）。
**誤判：** 合法紀錄在下列情況會無效，審查者須改寫後重留：寫到字元參照（含程式碼中，例：PR #3 實際紀錄「發現的問題」第 1 點以程式碼寫出 `&nbsp;` 與 `&#x7D50;`，(b) 原型判為「含字元參照」；改寫為文字描述後有效）；含 emoji 變體選擇符（例：✔️ 含 U+FE0F）；散文中的 `a<b`；HTML 註解；逐項表後沒有空行；「發現的問題」中以程式碼區塊貼出表格範例（現行已無效）。PR #1、PR #2 的實際紀錄（補 R-15 列）、第 2 節範本、`n < 3`、`` `<script>` ``、`` `Array<string>` ``、`12:30-13:00` 都維持有效（原型實測）。**成本：** 低。`review-gate.mjs` 約增加 40 行、`check-pr-body.mjs` 約 15 行；單元測試以上表 30 個案例與上述誤判、維持有效的案例為資料。**殘餘風險：** 本表以外、尚未發現的渲染轉換；同義詞（例：`Result:`）與語意矛盾（例：「不是同一模型」也含「同一模型」）仍由審查與產品負責人抽查（AC-EQ-5）處理。

**(c) 限定極小語法子集。** 紀錄的每一行都必須是下列之一，否則整則無效：第 1 行標記；`## 審查紀錄`；空行；七個欄位行 `- 結果：`、`- 針對 commit：`、`- 審查者：`、`- 作者：`、`- 獨立性：`、`- 審查依據：`、`- 已載入 skill：`（依此順序、各恰好一行）；`### 逐項結果`；逐項表（表頭、分隔列、R-1～R-15 依序各一列）；`### 發現的問題`；之後每一行以 `<數字>. `、`- ` 或三個空格加 `- ` 開頭，或為 `（無）`。欄位值、說明欄與發現的問題只允許下列以外的字元：`<`、`>`、`&`、`|`（說明欄除外）、`\`、`[`、`]`，以及 (b) 的 X1～X4。**誤判：** 最多。三則實際紀錄都會無效（PR #1 有「### 本機重跑與 CI」一節、PR #2 有第八個欄位行「- 性質：」與「### 檢查結果」一節、PR #2 與 PR #3 結尾有 `---` 與含連結的 `_Generated by [Claude Code](…)_`、PR #3 有「上工檢查」段落）；審查 agent 的寫法要依新格式調整，第 2 節範本與 R-1 的寫法說明需改寫。**成本：** 程式中等（逐行比對比 (a) 簡單），流程成本高（每位審查者都要改變寫法，格式錯誤時重留紀錄的次數增加）。**殘餘風險：** 最低，只剩允許的自由文字中的語意內容。

## 5. 已知限制

- CI 只能確認紀錄存在且格式正確，無法確認審查真的做過（需求第 9 節已接受）。產品負責人在 UAT 前抽看（AC-EQ-5）。
- 工作階段識別由 agent 自行填寫，CI 無法驗證真偽。
- 有寫入權限者可以直接以 API 寫入 `review-record` 狀態；分支保護指定來源為 GitHub Actions 可擋下以個人權杖寫入的狀態。
- 機械檢查只能證明驗收測試有執行斷言，不能證明斷言驗證了驗收標準；這部分由 R-15 與變異檢查把關（spec.md 12.2.1「殘餘風險」）。
- 第一個 PR（加入本機制的 PR）不受本檢查把關，由產品負責人人工確認；`review-record` 在 PR-1 之後的第一個 PR（**PR-1b**，v0.5；原為 PR-2）寫入過一次後、合併前加為必要檢查（spec.md 12.6 步驟 4、6b、8；DQ-8 已由產品負責人接受，處理方式見 spec.md 12.6「EQ-2 啟動例外的處理」；main 上的 review-gate 無法寫入狀態時，不論是第一次執行或之後的版本，見 DQ-11）。
- 本檢查永遠以預設分支上的 `review-gate.mjs` 判定。修改本檢查的 PR 由修改前的版本判定，修改在合併後才生效：PR-1b（實作 v0.5、v0.5.1 的第 4 節）由 PR-1 版判定；PR-1c（實作 DQ-14 的決定，v0.6 新增）由 PR-1b 版判定。處理方式都是新版 `--dry-run` 試算＋人工確認清單（spec.md 12.6「PR-1b 由舊版判定」「PR-1c 由 PR-1b 版判定」）。v0.6 起（產品負責人 2026-11-10 21:37 同意），PR-1b 版不做步驟 8b；PR-1c 合併後開**一次**探測 PR B，觀察最終版本在平台上的第一次執行（spec.md 12.6 步驟 8b）。
- PR-1b 版、PR-1 版的偵測形式都有 4.1 表中的繞過（讀者與 review-gate 看到不同內容）；處理方式依 DQ-14 決定。決定與 PR-1c 合併之前，這些寫法由審查 agent 依第 2 節撰寫、產品負責人抽查（AC-EQ-5）補足。
