## 1. 本文件是什麼

**本文件不是翻牌記憶遊戲的需求，也不是完整的工作規範。** 完整規範是 agent-dev-workflow skill；本文件只記錄本專案對該 skill 的調整與補充。

- 開始工作前，先讀 agent-dev-workflow，再讀本文件。
- 衝突時的優先順序依 agent-dev-workflow 第 2 節。
- 本文件的內容不是產品功能：不寫進規格書、程式碼或測試，不在需求文件的追溯矩陣中建立編號。

## 3. 對 agent-dev-workflow 的調整

| 編號 | 調整 | 理由 |
|---|---|---|
| W-1 | 所有 agent 都是同一個模型（Claude）在獨立工作階段中執行的子 agent。依 agent-dev-workflow 第 3.2 節維持獨立性：每個子 agent 以全新上下文啟動，只讀派工指令與文件，不讀其他 agent 的推理過程。審查紀錄須註明「審查者與作者為同一模型的不同工作階段」 | 本環境沒有不同模型或人類開發者可擔任審查者 |
| W-2 | 統籌 agent 是與產品負責人對話的 Claude，負責派出子 agent，並在每份派工指令中依第 4.1 節要求載入 skill | 確保子 agent 確實讀取 skill |
| W-3 | 版本庫內的 `.claude/skills/agent-dev-workflow/` 與 `.claude/skills/requirements-spec/` 是產品負責人維護之 skill 的快照副本。agent 不得修改，只能依 agent-dev-workflow 第 7.4 節第 5 點提出建議；產品負責人更新原始 skill 後，再以 Pull Request 同步副本 | 讓任何環境打開本專案都能取得 skill，同時保留產品負責人的維護權 |

## 4. 確保 agent 讀取 skill

skill 是否自動載入沒有保證，因此本專案疊用四層做法。

| 層 | 做法 | 位置 | 作用 |
|---|---|---|---|
| 4.1 派工指令 | 統籌 agent 派出每個子 agent 時，指令第一步寫明：「先用 Skill 工具載入 agent-dev-workflow 與本階段 skill，完成上工檢查，並把結果放在回覆開頭」 | 統籌 agent 的派工內容 | 讓 agent 讀取 |
| 4.2 常駐提醒 | 版本庫根目錄的 `CLAUDE.md` 與 `AGENTS.md` 寫明上工前先載入 skill，並列出底線規則 | `CLAUDE.md`、`AGENTS.md` | 讓 agent 讀取；skill 沒載入時底線仍在 |
| 4.3 子 agent 定義 | `.claude/agents/` 的子 agent 定義以 `skills` 欄位預先載入 skill。已知此欄位曾有未生效的回報，因此只作為額外一層 | `.claude/agents/*.md` | 讓 agent 讀取 |
| 4.4 可檢查的證明 | Pull Request 範本要求填寫上工檢查結果，以及已載入 skill 的變更紀錄最新版本號。版本號只寫在 skill 中，沒讀過就填不出來。審查 agent 以此為審查清單第一項；階段 3 的第一批變更加入 CI 檢查，確認 Pull Request 說明含這兩段 | `.github/pull_request_template.md`、審查清單、CI | 發現沒讀 |

`CLAUDE.md` 與 `AGENTS.md` 不得寫入任何 skill 的版本號，以免 4.4 的證明失效。

非 Pull Request 的產出（例如設計文件）在交付摘要開頭附上相同的兩段。

### 9.4 缺陷的定義與分類

**缺陷**：使產出（需求、設計、程式、測試、設定、skill、流程文件）不符合需求、設計、規範或其自身宣稱，且必須修改產出才能解決的問題。純粹的寫法偏好不算缺陷；打磨型問題算缺陷，但嚴重度為「打磨型」。

每個缺陷記一列，欄位為：編號（`D-PR<號碼>-<序號>`）、一句話描述、(1) 發現關卡、(2) 源頭階段、(3) 外部因素、(4) 嚴重度、(5) 是否擋住合併、(6) 是否發生在把關機制內、審查紀錄原用語（若有）、證據連結（最先發現的那筆紀錄；沒有時寫「無證據連結」並說明來源）、處理方式與所在 commit。

**(1) 發現關卡**：只記最先發現的一個。「最先」以證據的時間為準：CI 執行的完成時間、評論或回報的建立時間、commit 時間。同一時間有兩個以上時，以自動檢查優先。依下列順序判斷，取第一個符合的。

前四列只採計**在 CI（GitHub Actions）上的執行**，而且**失敗訊息本身指向這個缺陷**；只顯示工作失敗、要讀日誌才知道原因的（例如逾時），不算由該檢查發現。作者推送前在本機執行測試而發現的，歸「作者自我檢查」；非作者的 agent 在本機執行測試而發現的，歸其所屬關卡（測試 agent 歸「驗收測試撰寫」、審查 agent 歸「PR 審查」、統籌 agent 歸「統籌 agent」）。

| 關卡 | 判定條件 |
|---|---|
| PR 說明檢查 | `pr-body` 在 CI 上失敗，訊息指向此缺陷 |
| 驗收編號檢查 | `acceptance-ids` 在 CI 上失敗，訊息指向此缺陷 |
| 單元測試 | `tests/unit/` 的模組單元測試在 CI 上失敗，訊息指向此缺陷 |
| 驗收測試 | `tests/acceptance/`（無瀏覽器層或端對端層）的測試在 CI 上失敗，或其執行結果檢查（略過、未執行、零斷言、吞掉的失敗）失敗，訊息指向此缺陷 |
| 審查紀錄閘門 | `review-record` 在平台上的判定與預期不符（例如合法紀錄被判無效、無效紀錄被判有效）而揭露 |
| 變異檢查 | 任何人以變異檢查（故意改壞規則，看測試是否失敗）揭露測試或檢查的缺口 |
| 平台觀察 | 在 GitHub Actions 的實際執行中被觀察到，且不屬於以上各列（例如工作卡住、逾時、外部服務變慢，原因要讀日誌才知道）；部署到 GitHub Pages 的版本上的發現不屬此列，歸「系統測試」或「產品負責人」 |
| 系統測試 | 階段 4 系統測試中，測試 agent 在部署版本上測試、做探索式測試或量測非功能需求時發現 |
| 驗收測試撰寫 | 測試 agent 撰寫驗收測試，或在本機執行驗收測試時，發現程式或設計的缺陷（測試 agent 不是該程式的作者） |
| 下游 agent 回報 | 下游 agent 依輸入文件工作時發現上游的缺漏或矛盾，停下回報 |
| 作者自我檢查 | 作者在交付（推送或開 PR）前自己發現並修正自己產出中的缺陷，包括在本機執行測試 |
| 設計審查 | 對設計文件的獨立審查（不在 PR 上）提出 |
| PR 審查 | 審查 agent 在 PR 上以閱讀與判斷提出，包括它在本機執行測試或試算後提出的（它重做的變異檢查歸「變異檢查」） |
| 統籌 agent | 統籌 agent 以閱讀、調查日誌或比對提出 |
| 產品負責人 | 產品負責人提出 |

- 探測 PR 是發生場合，不是關卡；在探測 PR 上發現的缺陷，同樣依上表判定。
- 以**構造輸入或離線試算**揭露的檢查漏洞（例如構造一則能繞過 review-gate 的紀錄），歸執行試算者所屬的關卡：審查 agent 歸「PR 審查」、設計 agent 歸「設計審查」、作者歸「作者自我檢查」、測試 agent 歸「驗收測試撰寫」或「系統測試」、統籌 agent 歸「統籌 agent」、其他下游 agent 歸「下游 agent 回報」。

**(2) 源頭階段**：缺陷被引入的產出屬於哪個階段。

| 源頭 | 判定條件 |
|---|---|
| 需求 | 需求文件 |
| 設計 | 設計文件（含模組測試標準、驗收測試計畫） |
| 實作 | 程式、建置與檢查腳本、CI 工作流程設定、`tests/unit/` 的模組單元測試（由實作 agent 負責） |
| 測試 | 驗收測試與 `tests/support/`（由測試 agent 負責） |
| skill 與流程文件 | skill、`docs/workflow.md`、`CLAUDE.md`、`AGENTS.md`、PR 範本 |
| PR 說明與紀錄 | PR 說明、審查紀錄、驗證紀錄本身的錯誤（研究數據紀錄本身的錯誤不算開發缺陷，依 9.5 以更正評論處理） |
| 版本庫與平台設定 | 分支保護、版本庫設定、Pages 設定等在 GitHub 介面上的手動設定 |

**(3) 外部因素**：是／否。「是」表示問題主要由本專案無法控制的外部服務或平台行為造成（例如 GitHub 執行器、套件下載站），此時源頭階段記「讓它造成影響的那個產出」（例如沒有逾時的 CI 設定記「實作」）。

**(4) 嚴重度**：以缺陷**若未修正時的影響**判定，不看它在流程中是否擋住合併；由分類者依下列定義判定，不直接沿用審查紀錄上的用語。

| 嚴重度 | 定義 |
|---|---|
| 阻擋型 | 符合下列任一項：(a) 會讓產品違反 Must 需求；(b) 讓某道把關**漏判**——使不合格的變更通過、可被繞過或靜默通過；(c) 讓某道把關**誤擋所有變更**，使任何 PR 都無法合併；(d) 下游沒有任何合理讀法可以繼續，必須等上游決定 |
| 修正型 | 與需求、設計、規範或自身宣稱不符，但不屬阻擋型（包括只讓部分變更被誤擋、卡住或需要重跑的把關缺陷，以及下游有合理讀法可以繼續的空白） |
| 打磨型 | 不影響行為與判定，只影響可讀性、一致性或維護 |

**(5) 是否擋住合併**：是／否。該缺陷在流程中是否實際讓 PR 無法合併（例如審查結論為 CHANGES_REQUESTED、必要檢查失敗），與嚴重度分開記錄。

**(6) 是否發生在把關機制內**：是／否（CI 設定、檢查腳本、review-gate、審查流程文件屬於把關機制）。

無法判斷時寫「無法判斷」並附理由，不硬歸類。
